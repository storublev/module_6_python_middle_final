# Наблюдаемость: логи и мониторинг ошибок

Централизованные логи (ELK) и сбор ошибок (Sentry) для сервисов кинотеатра —
задания 1 и 4 девятого спринта.

> **Статус: заготовка.** Файлы описаны и согласованы между собой, но живым
> запуском не проверялись, и сервисы кинотеатра пока не шлют сюда логи.
> План — [docs/planning-sprint9.md](../../docs/planning-sprint9.md), эпик E5.

## Зачем это

В консоли разработчика логи видно, а на бою — нет: сервисов много, они на
разных машинах, контейнер пересоздали — логи пропали. Путь «положить логи в
базу рядом с данными» не работает: логи всё равно лежат отдельно у каждого
сервиса, растёт нагрузка и объём базы, а при её недоступности разом теряются и
сервис, и возможность понять, что случилось. Отдельная общая база логов решает
не всё: искать в ней по-прежнему неудобно и каждый сервис нужно учить единому
формату. Отсюда ELK: хранилище, приспособленное к поиску, плюс интерфейс.

Sentry отвечает за другое: неотловленные исключения со стектрейсом, контекстом
запроса и группировкой. Логи говорят, что происходило; Sentry — что сломалось.

## Что здесь

| Файл | Что описывает |
|---|---|
| `docker-compose.yml` | Elasticsearch для логов, Logstash, Kibana, Filebeat; Sentry — под профилем `sentry` |
| `logstash.conf` | входы (gelf от Docker и beats от Filebeat), разведение по индексам |
| `filebeat.yml` | чтение JSON-лога nginx и отправка в Logstash |

```sh
# ELK
docker compose -f deploy/observability/docker-compose.yml up -d
# Kibana — http://localhost:5601, Elasticsearch логов — http://localhost:9201

# Sentry (пять контейнеров, поэтому под профилем)
docker compose -f deploy/observability/docker-compose.yml --profile sentry up -d
docker compose -f deploy/observability/docker-compose.yml exec sentry-api sentry upgrade
```

## Решения, которые уже приняты

* **Elasticsearch для логов — отдельный.** Каталог фильмов Async API живёт в
  своём кластере; держать логи там нельзя — всплеск логов утащит за собой поиск
  по фильмам. Порт снаружи тоже свой (9201), чтобы их нельзя было перепутать.
* **Сервисы не шлют логи напрямую в Logstash.** Так делают в уроке
  (`python-logstash` прямо в приложении), но это привязывает код к системе
  логирования: сменится ELK — придётся править каждый сервис. Сервисы пишут в
  stdout или в файл, а доставку берёт на себя сборщик — `filebeat` или
  gelf-драйвер Docker.
* **Filebeat, а не второй Logstash.** Logstash тяжёл: JVM плюс разбор
  сообщений. Рядом с сервисами ставятся лёгкие Beats (есть ещё Metricbeat для
  метрик сервера, Packetbeat, Heartbeat).
* **Sentry не в общем compose.** Пять контейнеров, которые не нужны при каждом
  прогоне тестов; DSN приходит переменной окружения, и с пустым значением
  сервисы работают как обычно. Боевой вариант — `getsentry/self-hosted` или
  облачный sentry.io: тогда от этих контейнеров остаётся одна переменная.

## Что осталось сделать (эпик E5)

* nginx пишет access-лог в JSON в общий том, filebeat его читает;
* журналы сервисов приводятся к единому JSON-формату с `X-Request-Id`
  (заголовок проставляется с седьмого спринта — его достаточно протащить в
  запись журнала);
* Data View в Kibana и проверка: по одному `request_id` находится весь путь
  запроса через сервисы;
* Sentry подключается к сервисам через `sentry-sdk`, чувствительные данные
  маскируются;
* живая проверка: исключение в сервисе видно в Sentry, запись — в Kibana.
