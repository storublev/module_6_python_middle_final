# ETL событий: Kafka → ClickHouse

Непрерывно переносит пользовательские события из брокера в аналитическое
хранилище. События туда кладёт [сервис сбора](../ugc/README.md), забирают из
хранилища аналитики.

```
ugc ──► kafka (ugc.events) ──► ugc-etl ──► clickhouse (ugc.events) ──► аналитик
```

## Что здесь важно

**Смещения подтверждаются после вставки, а не после чтения.** Автокоммит
выключен: он подтверждал бы прочитанное по таймеру, и падение между чтением и
вставкой стоило бы пачки событий. Отсюда гарантия at-least-once — пачка может
повториться, но не пропасть.

**Повторы — не беда.** Таблица в ClickHouse — `ReplacingMergeTree` с
`event_id` в ключе сортировки: одинаковые события схлопываются при слиянии
кусков. Запросы, которым дубликаты недопустимы прямо сейчас, добавляют `FINAL`
или группируют по `event_id`.

**Вставка только пачками, и пачка действительно копится.** Каждая вставка в
MergeTree создаёт на диске новый кусок, который потом сливается с остальными;
вставлять события по одному — получить `too many parts` вместо аналитики. При
этом `poll()` отдаёт столько сообщений, сколько уже лежит в буфере клиента, а
`max_poll_records` — только верхняя граница. Поэтому ETL копит сообщения сам:
пачка уходит в хранилище, когда набралось `UGC_ETL_BATCH_SIZE` событий (по
умолчанию 10 000) или прошло `UGC_ETL_BATCH_MAX_WAIT` секунд (30) — смотря что
раньше. Второе условие нужно ночью, когда пачка не наберётся никогда, а
задержка доставки ограничена пятью минутами.

**Подтверждаются смещения ровно тех сообщений, что уехали в хранилище**, а не
текущая позиция потребителя: за время накопления клиент успевает прочитать
вперёд, и подтверждение позиции потеряло бы сообщения из накопителя.

**Устойчивость к сбоям обеих сторон.** Вставка повторяется с экспоненциальной
паузой (со случайным разбросом, чтобы несколько экземпляров ETL не вернулись к
хранилищу разом); после нескольких неудач подряд размыкается прерыватель, и
ETL ждёт, вместо того чтобы долбить лежащее хранилище. Пока он ждёт, события
копятся в Kafka — там они живут неделю. Пачку ETL не бросает: смещения не
подтверждены, и потерять её нельзя.

**Испорченное сообщение не останавливает перенос.** Сообщение, которое не
разбирается как JSON или не приводится к строке, пропускается с записью в
журнал: упасть на нём значило бы перезапуститься, прочитать его снова и упасть
опять — навсегда. Потеря одного события укладывается в допустимые 0,1%
(НФТ-4), остановка переноса — ни во что.

**Мониторинг памяти** (НФТ-12). ETL работает неделями, и утечка в нём
проявляется не падением, а ростом RSS. Раз в `UGC_ETL_MEMORY_REPORT_EVERY`
пачек в журнал пишется текущее потребление и его рост относительно старта, а
при переходе `UGC_ETL_MEMORY_LIMIT_MB` — предупреждение. Само приложение при
этом ничего не «чинит»: перезапускать контейнер решает оркестратор.

Чтобы росту памяти неоткуда было взяться: события обрабатываются пачками и
нигде не накапливаются, преобразование в строки идёт генератором (второй копии
пачки не появляется), глобальных кешей и растущих списков в ETL нет — только
числовые счётчики.

## Схема хранилища

[`schema/001_events.sql`](schema/001_events.sql) — таблица событий, витрина
популярности фильмов и материализованное представление, которое её наполняет.

* `ugc.events` — `ReplacingMergeTree`, партиции по месяцу, ключ сортировки
  `(event_type, occurred_at, event_id)`: почти каждый аналитический запрос
  фильтрует по типу события, а внутри типа данные идут по времени. TTL — три
  года (НФТ-8).
* `ugc.film_daily` — `AggregatingMergeTree` с дневными агрегатами по фильмам:
  просмотры, уникальные зрители, средняя доля просмотра. Досчитывается при
  вставке, поэтому вопрос «самые просматриваемые фильмы за месяц» читает
  тысячи строк витрины вместо сотен миллионов строк событий.

Колонки плоские: ClickHouse читает только те, что нужны запросу, а разбор JSON
на каждой строке съел бы весь выигрыш. Вместо `Nullable` — нули и пустые
строки: `Nullable` хранит отдельную колонку с признаком и хуже сжимается.

Вопросы, ради которых всё это заводилось (ФТ-9):

```sql
-- Самые просматриваемые фильмы за месяц — из витрины.
SELECT film_id, countMerge(views) AS views, uniqMerge(viewers) AS viewers
FROM ugc.film_daily
WHERE day >= today() - 30
GROUP BY film_id
ORDER BY views DESC
LIMIT 20;

-- Какие фильмы не досматривают: средняя доля просмотра ниже половины.
SELECT film_id, avgMerge(watched_ratio) AS finished, countMerge(views) AS views
FROM ugc.film_daily
WHERE day >= today() - 30
GROUP BY film_id
HAVING views > 100 AND finished < 0.5
ORDER BY finished ASC
LIMIT 20;

-- Какими фильтрами поиска пользуются.
SELECT name, value, count() AS used
FROM ugc.events
ARRAY JOIN filters.keys AS name, filters.values AS value
WHERE event_type = 'search_filters_applied' AND occurred_at >= now() - INTERVAL 7 DAY
GROUP BY name, value
ORDER BY used DESC
LIMIT 20;
```

## Запуск

Вместе со всем стеком кинотеатра:

```bash
docker compose up -d --build clickhouse ugc-etl
docker compose logs -f ugc-etl
```

Проверить, что события доезжают:

```bash
docker compose exec clickhouse clickhouse-client --query \
    "SELECT event_type, count() FROM ugc.events GROUP BY event_type"
```

Локально, без Docker:

```bash
pip install -r ugc_etl/requirements.txt
cd ugc_etl/src
export UGC_ETL_KAFKA_BOOTSTRAP_SERVERS=localhost:9092 UGC_ETL_CLICKHOUSE_HOST=localhost
python main.py
```

Остановка — SIGTERM (`docker compose stop ugc-etl` или Ctrl+C): текущая пачка
доезжает до хранилища, смещения подтверждаются, и только потом процесс
выходит.

## Тесты

**Unit-тесты** — порядок вставки и подтверждения, поведение при сбоях
источника и приёмника, преобразование событий в строки, повторы, прерыватель и
сторож памяти. Docker не требуется:

```bash
pip install -r ugc_etl/tests/unit/requirements.txt
pytest ugc_etl/tests/unit
```

**Линтеры:**

```bash
cd ugc_etl && flake8 . && ruff check .
```

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `UGC_ETL_KAFKA_BOOTSTRAP_SERVERS` | `localhost:9092` | Адреса брокеров через запятую |
| `UGC_ETL_KAFKA_TOPIC` | `ugc.events` | Топик событий |
| `UGC_ETL_KAFKA_GROUP_ID` | `ugc-etl` | Группа потребителей: экземпляры делят партиции |
| `UGC_ETL_KAFKA_AUTO_OFFSET_RESET` | `earliest` | С какого места читать при первом запуске |
| `UGC_ETL_BATCH_SIZE` | `10000` | Сколько событий копить перед вставкой |
| `UGC_ETL_BATCH_MAX_WAIT` | `30` | Сколько секунд ждать, если пачка не набралась |
| `UGC_ETL_POLL_TIMEOUT` | `5` | Сколько ждать одного ответа брокера, секунд |
| `UGC_ETL_CLICKHOUSE_HOST` / `_PORT` | `localhost` / `8123` | Адрес хранилища |
| `UGC_ETL_CLICKHOUSE_USER` / `_PASSWORD` | `default` / — | Доступ к хранилищу |
| `UGC_ETL_CLICKHOUSE_DATABASE` / `_TABLE` | `ugc` / `events` | Куда вставлять |
| `UGC_ETL_INSERT_RETRIES` | `5` | Повторы вставки |
| `UGC_ETL_INSERT_BACKOFF_BASE` / `_CAP` | `0.5` / `30` | Первая и наибольшая пауза между повторами, с |
| `UGC_ETL_BREAKER_FAILURES` / `_RESET_TIMEOUT` | `5` / `30` | Сбоев подряд до размыкания прерывателя и пауза, с |
| `UGC_ETL_MEMORY_REPORT_EVERY` | `10` | Раз во сколько пачек замерять память |
| `UGC_ETL_MEMORY_LIMIT_MB` | `512` | При каком потреблении предупреждать |
| `UGC_ETL_LOG_LEVEL` | `INFO` | Уровень журнала |
