# Исследование хранилищ: ClickHouse и Vertica

Задание 5 модуля: выбрать аналитическое хранилище для событий — сгенерировать
данные, выполнить агрегационные запросы, сравнить скорости, в том числе под
нагрузкой и в несколько потоков.

В кинотеатре 60 000 000 событий в сутки ([расчёт](../docs/requirements.md#метрики-нагрузки)),
хранить их нужно три года, а агрегирующий запрос должен укладываться в десять
секунд (НФТ-7). Вопрос исследования простой: какое из двух колоночных хранилищ
это выдержит и какой ценой.

## Что меряем

| Замер | Почему он |
|---|---|
| Вставка, строк/с | Хранилище должно принимать 60 000 000 строк в сутки (в среднем ~700 строк/с, в пик — 4 200). Не успевает — разговор окончен |
| Чтение на загруженных данных | Те самые вопросы аналитики (ФТ-9): топ фильмов, недосмотры, популярность жанров, разрез по платформам, полный скан |
| Чтение под нагрузкой | То же, но при непрерывной записи. Это и есть продакшен: аналитик приходит не в тишину |
| Место на диске | Во что превращаются 10 000 000 событий после сжатия — от этого зависит стоимость трёхлетнего хранения |

Условия одинаковы для обоих: одна машина, один диск, одни и те же данные (один
генератор с фиксированным зерном), одни и те же запросы, одинаковый размер
пачки при вставке, одинаковые ограничения по процессорам и памяти в compose.

## Данные

Генератор — [`generate.py`](generate.py). Данные не равномерно случайные, а
правдоподобные, иначе исследование потеряло бы смысл: на равномерном шуме
любое колоночное хранилище выглядит одинаково хорошо, а вопрос «какие фильмы
смотрят чаще» не имеет ответа.

* фильмы распределены по Парето — несколько хитов и длинный хвост;
* время событий размазано по году с вечерним пиком;
* доля просмотра — бета-распределение со смещением к единице и левым хвостом
  (часть фильмов бросают в начале — именно это ищет аналитика);
* типы событий — в тех же пропорциях, в каких их шлёт клиент.

Идентификаторы собираются из чисел, а не берутся случайными: так оба
хранилища получают **ровно один и тот же набор данных**, и сравнение честное.

Генерация десяти миллионов событий одним процессом идёт долго, поэтому она
разделена между процессами: каждый генерирует свой отрезок и льёт его сам.
Строки отдаются генератором пачками — десяти миллионов словарей в памяти не
появляется.

## Схемы

Обе схемы — в [`storages.py`](storages.py), рядом, чтобы видеть различия.

**ClickHouse:** `MergeTree`, партиции по месяцу, `ORDER BY (event_type,
occurred_at, film_id)`. Разреженный индекс по ключу сортировки — каждая
8192-я строка, — поэтому запрос с фильтром по типу события и времени читает
несколько гранул вместо всей таблицы.

**Vertica:** та же таблица с `ORDER BY` в проекции (в Vertica порядок
сортировки задаётся проекцией, а не таблицей) и сегментированием по хешу
`event_id` — так данные равномерно раскладываются по узлам, как рекомендует
сама Vertica.

Строки с малым числом значений — `LowCardinality(String)` в ClickHouse и
`VARCHAR` в Vertica: у Vertica словарное сжатие подбирается при загрузке само.

## Как запустить

```bash
# ClickHouse
docker compose -f research/docker-compose.yml up -d clickhouse
pip install -r research/requirements.txt
cd research && python bench.py all --storage clickhouse --rows 10000000 --report results-clickhouse.json

# Vertica
docker compose -f research/docker-compose.yml up -d vertica
cd research && python bench.py all --storage vertica --rows 10000000 --report results-vertica.json
```

Шаги можно запускать по отдельности: `prepare`, `load`, `read`,
`read-under-load`. Адреса и пароли — через переменные окружения
(`CLICKHOUSE_HOST`, `VERTICA_HOST` и далее), по умолчанию — localhost и порты
из `docker-compose.yml`.

## Результаты: ClickHouse

Прогон 21.09.2026, машина Apple M2 (8 ядер, 16 ГБ), Docker Desktop, контейнеру
отданы 4 ядра и 8 ГБ. Данные — 10 000 000 событий, пачки по 50 000, загрузка в
4 процесса. Сырые числа — [results-clickhouse.json](results-clickhouse.json).

**Вставка**

| Показатель | Значение |
|---|---|
| 10 000 000 строк загружены за | 41,0 с |
| Скорость вставки | **243 700 строк/с** |
| Объём на диске | **301 МБ** (≈ 31 байт на событие) |

Суточный поток кинотеатра — 60 000 000 событий — ClickHouse принимает за
четыре минуты; пиковые 4 200 событий в секунду он держит с запасом в полсотни
раз. Сжатие получилось лучше осторожной оценки из требований: 500 байт JSON
превращаются в 31 байт на диске (в 16 раз), то есть суточные 30 ГБ событий
занимают около 1,9 ГБ, а трёхлетнее хранение — порядка 2 ТБ.

**Чтение (медиана трёх прогонов)**

| Запрос | На загруженных данных | Под нагрузкой (2 пишущих процесса) |
|---|---|---|
| Топ фильмов по просмотрам | 0,02 с | 0,03 с |
| Недосмотренные фильмы | 0,02 с | 0,08 с |
| Популярность жанров за месяц | 0,01 с | 0,02 с |
| События по платформам и дням | 0,10 с | 0,16 с |
| Уникальные зрители, полный скан | 0,61 с | 0,74 с |

Во время замера «под нагрузкой» в таблицу дописали ещё 250 000 строк.
Требование НФТ-7 (агрегирующий запрос не дольше 10 секунд) выполняется с
запасом в десятки раз даже на полном скане, и непрерывная запись замедляет
чтение самое большее вчетверо — на числах это доли секунды.

Видно, за счёт чего: первые три запроса фильтруют по `event_type`, а он первый
в ключе сортировки, поэтому читается несколько гранул вместо всей таблицы.
Полный скан по `user_id` читает одну колонку из десяти — это и есть то самое
колоночное хранение.

## Результаты: Vertica

**Замерить не удалось: у Vertica больше нет бесплатной редакции.** Попытка
подробно, чтобы её не пришлось повторять:

1. Репозитория `vertica/vertica-ce` (и `opentext/vertica-ce`) на Docker Hub
   больше нет — ссылки из курса и документации отдают 404.
2. Публично доступен только `opentext/vertica-k8s` — тот же сервер Vertica
   (версия 26.2), собранный для оператора Kubernetes, amd64.
3. Одноузловой запуск из него собирается руками: создать пользователя
   `dbadmin`, выпустить самоподписанные сертификаты в
   `/opt/vertica/config/https_certs`, поднять агент управления узлом (NMA) и
   создать базу через `vcluster create_db` в режиме Eon (Enterprise в этом
   образе не поддерживается, нужны `--communal-storage-location` и
   `--shard-count`).
4. На последнем шаге сервер отвечает:

   > Community Edition (CE) license is deprecated and no longer supported in
   > OpenText Analytics Database (Vertica) 26.1 and later

То есть дело не в архитектуре процессора и не в эмуляции: **начиная с версии
26.1 Vertica не запускается без коммерческой лицензии**. Скрипты исследования
поддерживают Vertica (`--storage vertica`), и на машине с лицензией замер
делается той же командой; сравнить её с ClickHouse в этой работе нечем.

Что известно о Vertica из документации и что осталось непроверенным:

| Свойство | Vertica (по документации) | ClickHouse (замерено) |
|---|---|---|
| Хранение | Колоночное, проекции с собственным порядком сортировки и сегментированием | Колоночное, MergeTree с ключом сортировки и партициями |
| Вставка | Потоковая через WOS/ROS, рекомендуется COPY крупными порциями | 243 700 строк/с пачками по 50 000 |
| Масштабирование | Eon Mode: вычисления отделены от хранения, узлы добавляются под нагрузку | Шардирование и репликация через дистрибутивные таблицы |
| Оптимизатор | Database Designer подбирает проекции под конкретные запросы | Настройка ключа сортировки и проекций вручную |
| Лицензия | Коммерческая; с 26.1 бесплатной редакции нет | Apache 2.0 |

## ADR-5. Аналитическое хранилище — ClickHouse

**Контекст.** Нужно хранилище под 60 000 000 событий в сутки с трёхлетним
хранением и агрегирующими запросами не дольше десяти секунд (НФТ-7, НФТ-8).
Курс предлагает сравнить ClickHouse и Vertica.

**Варианты.**

1. **Vertica.** Зрелое аналитическое хранилище с Eon Mode и автоматическим
   подбором проекций. Но бесплатной редакции у неё больше нет (см. выше), то
   есть выбор Vertica — это сразу разговор о бюджете, а проверить её на своих
   данных до покупки нечем.
2. **ClickHouse.** Открытая лицензия, замеры на наших данных сделаны.

**Решение.** ClickHouse. Измеренные числа закрывают требования с запасом в
десятки раз, схема под наши вопросы уже написана
([ugc_etl/schema](../ugc_etl/schema/001_events.sql)), а лицензия не ограничивает
ни объём данных, ни число узлов.

**Последствия.** Дедупликация повторов ложится на `ReplacingMergeTree` и на
запросы (`FINAL` либо группировка по `event_id`) — в Vertica это решалось бы
иначе. Вставлять в ClickHouse можно только пачками, и это требование к ETL, а
не деталь: вставка по строке завалит хранилище кусками.

## Условия и оговорки

Замеры сделаны на одной машине (Apple M2, Docker Desktop, контейнеру отданы 4
ядра и 8 ГБ), а не на кластере: цель — проверить, укладывается ли хранилище в
наши требования, а не получить абсолютные числа для продакшена. На кластере
абсолютные значения будут другими.

Данные синтетические, хотя и с правдоподобными распределениями: настоящего
потока событий у кинотеатра пока нет — его как раз и собирает сервис из этого
спринта. Когда накопятся настоящие события, замер стоит повторить на них той
же командой.
