# Планирование восьмого спринта: сервис сбора пользовательских действий

Задание 1 модуля: декомпозировать работу, завести задачи в GitHub, оценить их
в story points и показать доску наставнику. Здесь — сама декомпозиция и
оценки; в GitHub задачи заводятся по этому документу скриптом
[`scripts/create_issues.sh`](../scripts/create_issues.sh).

## Как оцениваем

Оценка — story points по шкале Фибоначчи (1, 2, 3, 5, 8, 13). Значение чисел
зафиксировано до планирования, чтобы оценки участников означали одно и то же:

| SP | Что это значит |
|---|---|
| 1 | Делается в перерыве на кофе: правка конфигурации, короткий скрипт |
| 2 | Понятная работа на пару часов, неожиданностей не ждём |
| 3 | Понимаю, что делать, и справлюсь за день |
| 5 | День-полтора либо понятная работа с неизвестным куском |
| 8 | Трудная задача надолго: неизвестного больше, чем известного |
| 13 | Слишком крупно — обязательно разбить |

Оценивали по правилам planning poker: карточки открываются одновременно,
крайние оценки объясняют позицию, итог записывается в задачу. **Задачи с
оценкой больше 5 разбиты** — в спринт они попадают уже частями, поэтому
оценки 8 и 13 в таблице ниже не встречаются.

Исследовательские задачи (там, где до начала работы непонятно даже, что
получится) заведены отдельно и оценены временем, а не результатом: их итог —
решение и записанный ADR, а не работающий код.

## Роли

Модуль выполняется по командному треку в полном объёме, но команда из одного
человека, поэтому роли — не люди, а зоны ответственности. Они нужны, чтобы
задачи не перемешались: у каждой видно, чем она закончится.

| Роль | Зона ответственности |
|---|---|
| Архитектор | Требования, схемы AS IS/TO BE, ADR, обсуждение с наставником |
| Backend UGC | Сервис сбора событий: API, аутентификация, отправка в Kafka |
| Data | Kafka, ClickHouse, Vertica, исследование хранилищ, схема аналитического слоя |
| ETL | Перенос Kafka → ClickHouse, устойчивость, мониторинг памяти |
| QA/DevOps | compose, тесты, линтеры, нагрузочные прогоны, CI |

**Итого: 71 story point** на шесть эпиков. Критический путь проходит через
E2 → E3 → E4 → E6: исследование хранилищ (E5) зависит только от схемы данных,
поэтому идёт параллельно разработке API.

## Что можно делать параллельно

* E5 (исследование) не зависит от E4 (API): ему нужна только схема событий из
  задачи 17, а данные он генерирует сам.
* Задачи 10 (Kafka) и 11 (каркас сервиса) независимы: одна про инфраструктуру,
  другая про код.
* Задачи 23 (схема аналитики) и 12 (контракт событий) делаются вместе — это
  два конца одной трубы, и расходиться им нельзя.

## Определение Done

Задача закрыта, если:

* код в ветке спринта, коммиты — по одной логической части;
* линтеры (`flake8`, `ruff`) молчат, тесты проходят;
* поведение описано в README соответствующего сервиса;
* для решений с альтернативами записан ADR.
