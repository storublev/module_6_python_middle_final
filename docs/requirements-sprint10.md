# Требования к сервису уведомлений

Задание десятого спринта (тема «Проектирование коммуникационной системы»,
урок «Задание»): спроектировать сервис уведомлений онлайн-кинотеатра.
Требования выведены так же, как для [сервиса сбора событий](requirements.md) и
[сервиса пользовательского контента](requirements-sprint9.md): сначала
сценарии, потом числа, от которых считается оборудование.

Главное отличие от предыдущих спринтов: там пользователь **приходил сам** и
ждал ответа, здесь система **приходит к пользователю**. Поэтому бюджет времени
мягкий (минуты, а не миллисекунды), а цена ошибки высокая: письмо нельзя
отозвать, оно навсегда останется в почте клиента.

## Бизнес-описание, из которого всё выводится

Отдел маркетинга принёс три письма (урок «Гарри, тебе письмо!»):

| Письмо | Кому | Содержимое | Приоритет |
|---|---|---|---|
| Недельная подборка фильмов | всем зрителям, перед выходными | одинаковое для всех | высокий |
| Итоги месяца | активным (посмотрел ≥ 3 фильмов за месяц) | персональная статистика: сколько фильмов, какие жанры | высокий |
| Приветствие | новому зрителю, после регистрации | стандартный текст | низкий |

Плюс уведомления, которые рождаются из жизни сервиса: вышла новая серия
сериала, за рецензию зрителя проголосовали, в каталоге появились новинки,
в закладках давно лежит неначатый фильм.

Email — только начало. Маркетинг уже планирует SMS при входе и всплывающие
сообщения в браузере, поэтому **канал доставки должен быть сменным с первого
дня**, хотя реализован будет один.

## Ключевые сущности

| Сущность | Что это |
|---|---|
| **Событие** | Факт, из которого может родиться уведомление: «вышла серия», «проголосовали за рецензию», «наступила пятница». Приходит снаружи или рождается по расписанию |
| **Шаблон** | Вёрстка письма с переменными Jinja2, версионируется; принадлежит типу уведомления |
| **Тип уведомления** | Связка «событие → шаблон → канал → правила отправки» (мгновенное или откладываемое, как часто можно, в какое окно суток) |
| **Подписка** | Согласие зрителя получать уведомления определённого типа по определённому каналу; выключается в личном кабинете |
| **Уведомление** | Запись «кому, о чём, по какому шаблону»: `notification_id`, `content_id` и версия данных, о которой уже сообщили |
| **Отправка** | Факт доставки: кому, когда, каким каналом, с каким результатом; основа идемпотентности и статистики |
| **Рассылка** | Созданная менеджером в админ-панели пачка уведомлений на сегмент зрителей |

## Функциональные требования

| № | Требование |
|---|---|
| ФТ-1 | Любой сервис системы отправляет событие в API уведомлений одним быстрым запросом и не ждёт отправки письма |
| ФТ-2 | Событие принимается только с идентификатором, заданным отправителем (`event_id`): повтор запроса после потерянного ответа не создаёт второе уведомление |
| ФТ-3 | Мгновенные уведомления (новая серия, чек об оплате, приветственное письмо) доставляются без ожидания расписания |
| ФТ-4 | Откладываемые уведомления (голоса за рецензию, новинки каталога) накапливаются и отправляются одним письмом не чаще, чем разрешает тип уведомления |
| ФТ-5 | Генератор автоматических событий по расписанию создаёт периодические рассылки: недельная подборка, итоги месяца, напоминание о закладках |
| ФТ-6 | Генератор отличает «данные изменились» от «данные те же»: уведомление о новой серии не уходит второй раз, если с прошлого письма серия не сменилась |
| ФТ-7 | Менеджер создаёт в админ-панели рассылку на сегмент зрителей, проверяет её на себе и запускает — сразу или по расписанию |
| ФТ-8 | Шаблон письма, созданный менеджером, проверяется при сохранении: синтаксис, только разрешённый набор переменных, письмо рендерится |
| ФТ-9 | Письмо собирается единым шаблонизатором — и для автоматических уведомлений, и для рассылок менеджера |
| ФТ-10 | Зритель видит в личном кабинете список типов уведомлений и **отключает** любой из них, а также отписывается от всего сразу |
| ФТ-11 | Каждое письмо содержит ссылку отписки, работающую без входа в аккаунт |
| ФТ-12 | Время отправки считается в **часовом поясе зрителя**; вне разрешённого окна суток уведомление ждёт утра |
| ФТ-13 | Сервис хранит историю отправок и отдаёт её админ-панели: что, кому и когда ушло, чем закончилось |
| ФТ-14 | Отправка через внешний почтовый сервер выполняется с ограничением темпа, чтобы не получить бан и не уронить сервер |
| ФТ-15 | Сервис отдаёт документацию OpenAPI и проверки живости и готовности для оркестратора |

Отдельно про ФТ-8: без валидации менеджер (не разработчик) сохранит шаблон,
который уронит сборку письма или уйдёт в бесконечный цикл, — про это прямо
предупреждает урок «Как устроен почтальон Печкин?».

## Нефункциональные требования

| № | Требование |
|---|---|
| НФТ-1 | Мгновенное уведомление уходит не позже чем через **5 минут** после события (требование задания — «несколько минут») |
| НФТ-2 | Приём события укладывается в **100 мс** на 95-м перцентиле: API только проверяет контракт и кладёт в очередь |
| НФТ-3 | При падении **любого** компонента уведомление не теряется: событие переживает перезапуск API, очереди и воркера |
| НФТ-4 | Гарантия доставки — **at least once** плюс идемпотентность по ключу отправки, то есть на практике «ровно один раз» для зрителя |
| НФТ-5 | После простоя генератора автоматических событий повторный запуск не рассылает старые события заново и не пропускает новые |
| НФТ-6 | Воркеры масштабируются горизонтально: добавление воркера увеличивает пропускную способность без изменения кода и без дублей |
| НФТ-7 | Сбор данных для письма не мешает работе остальных сервисов: воркер ходит за ними с ограничением частоты, пачками и с таймаутами |
| НФТ-8 | Ночью зрителю не пишут: окно отправки по умолчанию 09:00–21:00 местного времени, тип уведомления может окно сузить |
| НФТ-9 | Зрителю уходит не больше заданного числа писем в сутки (единая политика контактов); превышение откладывается, а не теряется |
| НФТ-10 | Устаревшее событие не отправляется: воркер перед отправкой перепроверяет актуальность (серию уже посмотрели — письмо не нужно) |
| НФТ-11 | Персональные данные (email, имя) не попадают в журналы и в систему мониторинга ошибок |
| НФТ-12 | Каналы доставки сменные: добавление SMS или push не требует правок в API, генераторе и админ-панели |
| НФТ-13 | Сервис пишет журнал одной строкой JSON с `request_id`, как остальные сервисы проекта, и отдаёт спаны в Jaeger |
| НФТ-14 | Секреты (пароль приложения SMTP) задаются окружением и не имеют значений по умолчанию |

## Метрики нагрузки

### Исходные допущения

Числа продолжают расчёт восьмого и девятого спринтов: та же аудитория, та же
активность. Новые допущения касаются только рассылок.

| Допущение | Значение | Откуда |
|---|---|---|
| MAU | 5 000 000 | Целевая аудитория кинотеатра (восьмой спринт) |
| DAU | 1 000 000 | Stickiness 20% |
| Зарегистрированных зрителей | 10 000 000 | За месяц заходит половина зарегистрированных |
| Доля адресуемых (email подтверждён, не отписался) | 70% | Остальные отписались или не подтвердили адрес |
| Доля активных за месяц (≥ 3 фильмов) | 50% MAU | Условие письма «итоги месяца» |
| Новых регистраций в месяц | 100 000 | Прирост около 2% MAU |
| Сериалов с выходящими сериями | 200 | Каталог 50 000, из них с премьерами — малая часть |
| Подписчиков на сериал | 20 000 в среднем | Из 5 000 000 MAU сериал смотрит 0,4% |
| Окно рассылки на часовой пояс | 2 ч (7 200 с) | Письмо уходит между 10:00 и 12:00 местного времени |
| Доля аудитории в самом плотном поясе | 60% | Москва и Санкт-Петербург |
| Средний размер письма | 30 КБ | HTML с вёрсткой, картинки — ссылками |

### Сколько писем в сутки

```
Адресатов = 10 000 000 × 0,7 = 7 000 000

Недельная подборка  = 7 000 000 / 7 сут            = 1 000 000 писем/сут
Итоги месяца        = 5 000 000 × 0,5 × 0,7 / 30   ≈    58 000 писем/сут
Приветственные      = 100 000 / 30                 ≈     3 300 писем/сут
Новые серии         = 200 / 7 × 20 000 × 0,7       ≈   400 000 писем/сут
Прочие мгновенные   = порядка 10 000               ≈    10 000 писем/сут
                                                     ─────────────────────
Итого                                              ≈ 1 470 000 писем/сут
```

### Пик

Средний поток ничего не говорит: рассылка не размазана по суткам, а падает
окном. Худший случай — недельная подборка в самом плотном часовом поясе:

```
Писем в пиковом окне = 7 000 000 × 0,6 = 4 200 000
Пиковый темп         = 4 200 000 / 7 200 с ≈ 583 письма/с
```

Мгновенные уведомления добавляют к этому немного, но у них жёсткий срок
(НФТ-1). Худший случай — премьера популярного сериала: 20 000 подписчиков,
письма должны уйти за пять минут:

```
Пик премьеры = 20 000 / 300 с ≈ 67 писем/с
```

**Расчётная пропускная способность отправки — 650 писем/с.** Это и есть число,
от которого считается количество воркеров и допустимый темп внешнего почтового
сервера: при 20 письмах/с на соединение нужно порядка 33 параллельных
отправителей, то есть воркеры обязаны масштабироваться горизонтально (НФТ-6).

Приём событий нагружен несопоставимо меньше: периодические рассылки рождаются
**пачками** (одно событие на сегмент, а не на зрителя), поэтому API принимает
сотни запросов в сутки, а не сотни в секунду. Отсюда прямое следствие для
архитектуры: узкое место — не API, а воркер и внешний почтовый сервер.

### Объём данных

```
Подписки и настройки = 10 000 000 зрителей × 10 типов        = 100 000 000 записей
Подписки на сериалы  = 5 000 000 × 3 сериала                 =  15 000 000 записей
История отправок     = 1 470 000 писем/сут × 90 сут          ≈ 132 000 000 записей
```

При 200 байтах на запись история отправок — около 26 ГБ на квартал. Это
сопоставимо с объёмами UGC-сервиса, о чём урок предупреждает прямо. Значит,
история отправок хранится с ограниченным сроком жизни, а не вечно, и
агрегируется для отчётов маркетинга.

## Что осталось за границами

* **Маркетинговая сегментация** — урок «Единая политика контактов» прямо
  выводит её за рамки задачи. Сегмент приходит в рассылку готовым списком
  условий, сервис его только применяет.
* **SMS и push** — закладывается расширяемость (НФТ-12), реализуется email.
* **Отслеживание прочтения** (пиксель, MDN, переходы по ссылкам) — в модели
  предусмотрено поле результата отправки, но сбор фактов открытия писем не
  делается: почтовые сервисы всё жёстче относятся к трекингу, а для задания
  это не требуется.
