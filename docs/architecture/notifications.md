## Задание 1. Гибридная подготовка данных

Урок ставит развилку: данные для письма (email, имя, статистика просмотров)
собираются **до воркера** и приезжают к нему готовыми — или воркер собирает их
**сам**. У обоих вариантов есть режим, в котором они плохи:

* **собирать до воркера** — источник события ждёт, пока система соберёт данные
  на тысячи адресатов. HTTP-запрос админа «опубликовать серию» висит минутами,
  а сообщение в очереди раздувается до мегабайтов;
* **собирать в воркере** — для пачки на миллион адресатов воркер сделает
  миллион запросов в сервис авторизации и в UGC. Это ровно тот отказ
  подсистемы данных, от которого предостерегает задача урока про RabbitMQ.

**Гибрид разделяет два разных вида данных:**

| Вид данных | Кто собирает | Почему |
|---|---|---|
| **Что произошло** — `film_id`, `episode`, `review_id`, версия данных, сегмент получателей | **источник события**: он и так это знает, добывать нечего | Данные события уже в руках у того, кто его породил. Передать их — не работа, а заполнение полей |
| **Кому и как писать** — email, имя, язык, часовой пояс, подписки | **воркер**, пачками, с ограничением частоты | Это данные получателя, их всегда одинаково много, и они нужны в момент отправки, а не в момент события |
| **Персональная статистика** — сколько фильмов посмотрел, какие жанры | **генератор событий** заранее, пачкой на сегмент | Тяжёлый аналитический запрос; делать его на каждого получателя в воркере — миллион запросов вместо одного |

Правило одной строкой: **в сообщение кладётся идентификатор и версия, а не
содержимое; всё, что зависит только от получателя, воркер добирает сам; всё,
что считается одним запросом на всю пачку, считается до очереди.**

Это же прямо требует чек-лист проектного задания: «к воркеру не придёт адрес
email и ФИО получателя, будет только `user_id`, `template_id`, `subject` и
прочее. Он должен сам сходить в сервис авторизации за пользовательскими
данными».

### Сценарий 1. Часть сайта просит мгновенное уведомление

Пример: вышла новая серия сериала; UGC сообщает, что за рецензию зрителя
проголосовали; сервис авторизации сообщает о регистрации.

```
Источник → API /events → очередь notify.events → воркер-планировщик
        → очередь notify.render → воркер-сборщик → очередь notify.send → воркер-отправщик
```

1. **Источник** шлёт в API одно событие: тип, `content_id`, версия данных,
   `event_id` (его собственный ключ идемпотентности) и **признак адресата** —
   либо конкретный `user_id`, либо правило («подписчики сериала N»).
   Запрос лёгкий: API ничего не собирает, укладывается в 100 мс (НФТ-2).
2. **API** проверяет контракт, отбивает повтор по `event_id` и публикует
   сообщение в очередь. Источник свободен.
3. **Воркер-планировщик** разворачивает правило адресации в список получателей
   (подписчики сериала), отбрасывает отписавшихся и тех, кому по политике
   контактов сегодня уже хватит, и режет список на пачки по 1 000. Каждая пачка
   — отдельное сообщение в очередь сборки.
4. **Воркер-сборщик** на пачку делает **один** запрос в сервис авторизации за
   адресами и именами (batch-эндпоинт), рендерит Jinja2-шаблон на каждого
   получателя и кладёт готовые письма в очередь отправки. Перед рендером он
   **перепроверяет актуальность**: если зритель уже посмотрел эту серию,
   письмо не нужно (НФТ-10).
5. **Воркер-отправщик** отправляет письма через пул SMTP-соединений с
   ограничением темпа и отмечает факт отправки.

Данные события пришли из источника, данные получателей добрал воркер — это и
есть гибрид. Срок «несколько минут» выдерживается: тяжёлого нет ни на одном
шаге, а число воркеров каждого вида увеличивается независимо.

### Сценарий 2. Генератор автоматических событий, большая группа

Пример: недельная подборка фильмов перед выходными; итоги месяца; напоминание
про закладки.

```
Генератор (cron/шедулер) --витрина--> API /events (пачка сегментов)
        → очередь notify.events → ... дальше как в сценарии 1
```

1. **Генератор** по расписанию строит **витрину**: один тяжёлый запрос на
   сегмент, а не по запросу на зрителя. Для «итогов месяца» это агрегат из
   ClickHouse «зритель → сколько фильмов, топ жанров»; он ложится во временную
   таблицу и живёт до конца рассылки.
2. Генератор шлёт в API **события на сегмент**, а не на человека: одно событие
   = «рассылка X, сегмент Y, витрина Z, окно отправки такое-то». Миллион писем
   рождается из десятков сообщений — поэтому приём событий и не нагружен.
3. **Воркер-планировщик** разворачивает сегмент в получателей и режет на пачки
   — как в сценарии 1.
4. **Воркер-сборщик** берёт персональную статистику **из витрины по ключу**
   (дешёвое чтение), а адрес и имя — из сервиса авторизации пачкой.

Здесь гибрид виден лучше всего: **тяжёлое посчитано один раз до очереди**,
**лёгкое и зависящее от получателя** добирается в воркере.

Защита от повторов после простоя (НФТ-5): генератор не «просыпается и шлёт всё,
что накопилось». У каждой рассылки есть ключ запуска —
`(тип рассылки, период)`, например `weekly_digest.2026-W40`. Ключ пишется в
базу уникальным индексом до публикации события. Простоял генератор сутки —
после запуска он увидит, что запуск за прошлую неделю уже был (или что окно
рассылки закрылось), и не станет слать её повторно. Для уведомлений о данных
работает второй механизм — **хранимая версия**: в записи уведомления лежит
номер серии, о которой уже сообщили, и совпадение версий гасит событие.

### Сценарий 3. Ручная рассылка менеджера

```
Админка --сохранённый шаблон + сегмент--> API /campaigns
        → очередь notify.events → ... дальше как в сценарии 1
```

1. **Менеджер** в админке верстает письмо в шаблоне с разрешённым набором
   переменных, отправляет пробное письмо себе и выбирает сегмент.
2. При сохранении шаблон **валидируется**: синтаксис, только разрешённые
   переменные, и письмо действительно рендерится на тестовом наборе данных.
   Без этого менеджер однажды сохранит шаблон с бесконечным циклом.
3. Админка шлёт в API **одно** событие на рассылку: `template_id`, сегмент,
   канал, время запуска. Текст письма **не передаётся** — он лежит в хранилище
   шаблонов и достаётся по `template_id`. Это ответ на вопрос урока «как
   передаётся текст письма: с данными клиентов или из общего хранилища».
4. Кнопка «Запустить» = немедленная публикация события; «Запустить в 10:00» =
   запись в расписание, и дальше сценарий полностью совпадает со вторым.

Гибрид тот же: **сегмент и шаблон — от админки, получатели и их данные —
в воркере**.

### Итог задания 1

| | Источник события | Генератор | Админка | Воркер |
|---|---|---|---|---|
| Что произошло | **даёт** | даёт | даёт | — |
| Кого касается | правило или `user_id` | сегмент | сегмент | **разворачивает в список** |
| Тяжёлая статистика | — | **считает витриной** | — | читает из витрины по ключу |
| Email, имя, язык, TZ | — | — | — | **берёт пачкой из Auth** |
| Текст письма | — | — | `template_id` | **рендерит Jinja2** |
| Проверка актуальности | — | — | — | **делает перед отправкой** |

## Задание 2. Архитектура сервиса

### Компоненты

| Компонент | Что делает | Почему отдельный |
|---|---|---|
| **API уведомлений** (`notify_api`) | Принимает события и заявки на рассылку, проверяет контракт и идемпотентность, публикует в очередь. **Рассылкой не занимается** | Единственная дверь для событий: формат меняется в одном месте, а не во всех сервисах кинотеатра |
| **Брокер** (RabbitMQ) | Точка обмена `notify`, очереди по этапам, Dead Letter Exchange | Развязывает быстрый приём и медленную отправку; переживает падение любой стороны |
| **Воркер-планировщик** (`notify_planner`) | Разворачивает адресацию в получателей, применяет подписки и политику контактов, режет на пачки, откладывает до разрешённого часа | Единственное место, где решается «кому и когда» |
| **Воркер-сборщик** (`notify_render`) | Пачкой добирает данные получателей, проверяет актуальность, рендерит Jinja2 | Отделён от отправки: у сборки узкое место — чужие сервисы, у отправки — почтовый сервер. Масштабируются независимо |
| **Воркер-отправщик** (`notify_sender`) | Отправляет через канал (SMTP-пул, дальше SMS и push), пишет результат | То же: разный темп, разные отказы |
| **Генератор событий** (`notify_scheduler`) | По расписанию строит витрины и публикует периодические рассылки | Не влияет на остальной сайт, поэтому может работать медленно и тяжело |
| **Websocket-шлюз** (`notify_ws`) | Держит соединения зрителей и доставляет мгновенные уведомления в открытую вкладку | Долгоживущие соединения нельзя держать в том же процессе, что и обычный API |
| **Сокращатель ссылок** (`shortener`) | Выдаёт короткий ключ на длинный адрес, считает переходы, отдаёт 301/302 и 404 для просроченных | Нужен и письмам, и SMS; переходы по ссылкам — отдельная нагрузка на чтение |
| **Админка рассылок** | Шаблоны (CRUD), сегменты, запуск сразу, отложенно и повторяемо | Делается в существующей админке Django отдельным приложением — см. ADR-13 |
| **База уведомлений** (PostgreSQL) | Подписки, настройки, шаблоны, записи уведомлений с версией данных, расписания, история отправок | Данные связанные, нужны транзакции и уникальные индексы для идемпотентности |

### Очереди

Имена — по правилу урока `[микросервис].[действие-консьюмера]`:

| Очередь | Кто читает | Что лежит |
|---|---|---|
| `notify.plan` | планировщик | событие или заявка на рассылку |
| `notify.render` | сборщик | пачка получателей (до 1 000) со ссылкой на витрину и шаблон |
| `notify.send` | отправщик | готовое письмо: адрес, тема, тело, ключ идемпотентности |
| `notify.retry` | отложенный возврат | сообщения, отправленные в DLX и ждущие повтора |
| `notify.dead` | человек | то, что не удалось обработать после всех попыток |

Все очереди `durable`, публикация с `confirm`, сообщения — `delivery_mode=2`.
В заголовках каждого сообщения едет `X-Request-Id` того запроса, из которого
всё началось: без него в ELK не связать письмо с действием, которое его
породило. Мониторится **возраст самого старого сообщения** в каждой очереди —
это единственная метрика, по которой видно, что рассылка встала.

### Ключи маршрутизации

Отчётные события по правилу урока: `[сущность]-reporting.[версия].[событие]`.

```
user-reporting.v1.registered      → приветственное письмо
film-reporting.v1.episode-added   → уведомление подписчикам сериала
review-reporting.v1.voted         → откладываемое уведомление автору
campaign-reporting.v1.started     → ручная рассылка менеджера
```

Тело сообщения для одной сущности одинаково для всех её событий, различается
только ключ маршрутизации. Имени получателя в ключе нет: событие описывает
факт, а не адресата.

### Как выполняются требования задания

| Требование | Чем закрывается |
|---|---|
| Расширяемость на SMS и push | Канал — это реализация интерфейса `Channel.send(message)`; выбор канала лежит в типе уведомления и подписке. API, планировщик и админка о каналах не знают, добавление канала — новый воркер-отправщик и новая очередь |
| Мгновенные — за несколько минут | Ни один шаг не делает тяжёлой работы; очереди мгновенных уведомлений отделены от массовых рассылок приоритетом, поэтому недельная подборка не задерживает письмо о новой серии |
| Ничего не теряется при падении любого компонента | Событие переживает падение API (публикация с `confirm` до ответа клиенту), падение брокера (`durable` + `delivery_mode=2`), падение воркера (`ack` только после успеха). Гарантия — **at least once** |
| Отсутствие дублей | Поверх at-least-once — идемпотентность: уникальный ключ отправки `(notification_id, user_id, channel, период)` в базе. Повторно доставленное сообщение натыкается на запись и не шлёт письмо второй раз |
| Нет дублей после простоя генератора | Ключ запуска `(тип рассылки, период)` с уникальным индексом плюс хранимая версия данных в записи уведомления |
| Настройка уведомлений пользователем | Таблица подписок «зритель × тип × канал»; планировщик фильтрует по ней. Ссылка отписки в каждом письме работает по подписанному токену, без входа в аккаунт |
| Единая шаблонизация | Один сервис шаблонов и один рендерер Jinja2 и для автоматических уведомлений, и для рассылок менеджера. У менеджера ограничен набор переменных и включена валидация |
| Масштабируемость | Все три вида воркеров без состояния и читают свою очередь конкурентно; добавление процесса увеличивает пропускную способность. Узкое место — внешний почтовый сервер, поэтому темп отправки ограничивается настройкой, а не числом воркеров |

### Устойчивость: что делаем при отказах

Из задачи урока про RabbitMQ (её чек-лист — это, по сути, требования к нашему
воркеру):

* **временная ошибка внешнего сервиса** не должна крутить сообщение по кругу и
  вставать поперёк очереди: после трёх попыток сообщение уходит в **Dead Letter
  Exchange** и возвращается через `notify.retry` с задержкой (пауза с
  удвоением). Совсем безнадёжное садится в `notify.dead` и ждёт человека;
* **отказ подсистемы данных** (сервис авторизации лёг): сборщик видит серию
  отказов и **размыкает прерыватель** — перестаёт долбиться и возвращает
  сообщения в очередь. Письма не теряются, рассылка просто ждёт;
* **восстановление** — не лавина: число одновременных сборщиков и темп каждого
  регулируются настройкой, чтобы не уронить только что поднявшийся сервис
  повторно;
* **заливка большой рассылки** в очередь идёт с ограничением темпа публикации,
  чтобы всплеск записи не мешал другим очередям того же брокера.

Это те же приёмы, что уже применяются в проекте (повторы с паузой и circuit
breaker в `src/storage/resilience.py` Async API), поэтому реализация будет
опираться на существующий код, а не писаться заново.

### ADR-9. Брокер уведомлений — RabbitMQ, хотя в системе уже есть Kafka

**Контекст.** В проекте с восьмого спринта работает Kafka для потока событий
просмотра. Заводить второй брокер — это ещё один компонент в эксплуатации.

**Варианты.**

1. **Переиспользовать Kafka.** Плюс — ничего нового не разворачиваем. Минус —
   Kafka это журнал: потребитель двигает смещение по порядку, и «отложить одно
   сообщение на десять минут, остальные обрабатывать» в ней делается только
   отдельными топиками-таймерами. А это нужно постоянно: ночное окно, повтор
   после ошибки, отложенная рассылка. Нет и маршрутизации: адресация по типу
   события пришлось бы кодировать топиками.
2. **RabbitMQ.** Точки обмена и привязки дают маршрутизацию по ключу, а Dead
   Letter Exchange с TTL — штатный механизм отложенного повтора. Подтверждение
   на сообщение, а не смещение группы: медленное письмо не держит всю партицию.

**Решение.** RabbitMQ, точка обмена `notify` типа topic. Именно это называет и
урок «Брокер сообщений RabbitMQ», и чек-лист проектного задания («при
использовании RabbitMQ предусмотрите Dead Letter Exchanges»). Kafka остаётся
там, где она уместна, — в потоке событий просмотра.

**Последствия.** В стенде появляется ещё один брокер и его мониторинг. Зато
отложенный повтор и ночное окно не требуют собственного планировщика поверх
брокера. Гарантия — at-least-once, значит идемпотентность обязательна
(см. ADR-11).

### ADR-10. Три вида воркеров вместо одного

**Контекст.** Урок допускает и один воркер («формирует сообщение и, если он
один, отправляет»), и разделение на формирующие и отправляющие.

**Варианты.**

1. **Один воркер.** Проще: одна очередь, один процесс. Но у него два разных
   узких места в одном цикле — чужие сервисы при сборе данных и почтовый
   сервер при отправке. Масштабировать придётся по худшему из них, а
   прерыватель на сервис авторизации остановит и отправку уже собранных писем.
2. **Планировщик + сборщик + отправщик.** Три очереди и три процесса, но у
   каждого своя причина тормозить и своё число копий.

**Решение.** Три вида. Разворачивание сегмента в получателей — работа с базой
уведомлений, сборка — работа с сервисом авторизации и ClickHouse, отправка —
работа с почтовым сервером. Это три разных отказа, и смешивать их в одном
процессе значит связать их одной судьбой.

**Последствия.** Сообщение проходит три очереди, растёт задержка — но она в
секундах, а бюджет в минутах. Зато отказ почтового сервера не мешает собирать
письма впрок, а отказ сервиса авторизации не мешает отправлять собранные.

### ADR-11. Гарантия — at least once плюс идемпотентность, а не exactly once

**Контекст.** Урок «Что такое коммуникационная политика» перечисляет четыре
гарантии и называет идеальной exactly once. Письмо-дубль — самая частая
жалоба клиентов.

**Варианты.**

1. **At most once.** Дублей не будет никогда, но часть писем просто не уйдёт.
   Для приветственного письма и чека это недопустимо.
2. **Exactly once на уровне брокера.** RabbitMQ его не даёт, а внешняя
   отправка почты его дать не может в принципе: SMTP-сервер может принять
   письмо и не успеть ответить, и отправитель не знает, ушло оно или нет.
3. **At least once + ключ идемпотентности у получателя.**

**Решение.** Вариант 3. Доставка сообщения в воркер — at least once (требование
задания «ничего не должно потеряться»), а от дублей защищает **запись факта
отправки** с уникальным ключом `(notification_id, user_id, channel, период)`.
Перед отправкой воркер вставляет запись; конфликт уникальности означает, что
письмо уже ушло, и сообщение подтверждается без отправки.

**Последствия.** Окно на дубль остаётся ровно одно: письмо принято SMTP-сервером,
а запись не успела сохраниться. Оно закрывается тем, что запись вставляется
**до** отправки со статусом «в процессе» и переводится в «отправлено» после.
Тогда худший случай — письмо, отмеченное отправленным, но не ушедшее; это
видно в истории и чинится ручным повтором, что безопаснее дубля.

### ADR-12. Текст письма едет по `template_id`, а не в сообщении

**Контекст.** Прямой вопрос урока: текст письма передаётся вместе с данными
клиентов или берётся из общего хранилища.

**Решение.** В сообщении едет `template_id` и версия шаблона; тело берётся из
хранилища шаблонов.

**Почему.** На миллионной рассылке 30 КБ вёрстки в каждом сообщении — это
30 ГБ в брокере вместо десятков байт. Плюс шаблон становится общим для
автоматических уведомлений и рассылок менеджера, чего требует задание
(«единая система шаблонизации»). Версия в сообщении нужна, чтобы правка
шаблона посреди рассылки не разослала половине зрителей одно письмо, а
половине другое.

**Последствия.** Хранилище шаблонов становится зависимостью воркера-сборщика;
чтобы она не стала узким местом, отрендеренные шаблоны кешируются в процессе
по паре `(template_id, версия)`.

### ADR-13. Админка рассылок — приложение в существующей админке Django

**Контекст.** Чек-лист задания требует админ-панель для менеджеров, фреймворк
на своё усмотрение. В проекте уже работает админка каталога на Django 5.2,
встроенная в общий стек и пускающая сотрудников через сервис авторизации.

**Варианты.**

1. **Отдельная админка.** Свой контейнер, свой вход, свои права — и второй
   комплект того же самого.
2. **Приложение в существующей админке.** Вход сотрудника, права
   (`admin.access`), статика и маршрут `/admin/` уже есть.

**Решение.** Вариант 2: приложение `campaigns` в `admin_panel/`. Оно работает
с базой уведомлений, а не с базой каталога, — подключается вторым соединением.

**Последствия.** Появляется право `notifications.manage` в сервисе авторизации:
редактор каталога не должен уметь разослать письмо миллиону зрителей. Админка
получает вторую базу, и отказ базы уведомлений не должен ронять работу с
каталогом — обращения к ней идут с таймаутом и понятной ошибкой.

### ADR-14. Отправка — через SMTP-пул, с местом под транзакционный сервис

**Контекст.** Расчётная пропускная способность — 650 писем/с. Урок «Как
посылать быстрее» показывает, что установка SMTP-соединения занимает около
пяти секунд, и рекомендует пул, а на больших объёмах — транзакционный сервис
(Sendgrid, Mailgun, Amazon SES).

**Решение.** Отправщик работает через **пул SMTP-соединений** с настраиваемым
темпом; за интерфейсом `Channel` предусмотрена вторая реализация — HTTP-API
транзакционного сервиса.

**Почему не сразу транзакционный сервис.** Он требует внешнего аккаунта и
ключа, а на стенде и в тестах нужен локальный приёмник (`aiosmtpd`). Интерфейс
один, поэтому переключение — это настройка, а не переписывание.

**Последствия.** Лимиты внешних сервисов (Gmail — 500 писем в сутки) делают
полноценную нагрузочную проверку на настоящей почте невозможной: замеры
делаются на локальном приёмнике, а на реальном сервере проверяется только
корректность письма.

### ADR-15. Клиент брокера — aio-pika, а не pika из урока

**Контекст.** Урок называет `pika` самой известной библиотекой для RabbitMQ.
Наши воркеры асинхронные: asyncpg к базе, httpx к сервису авторизации,
aiosmtplib к почте.

**Решение.** `aio-pika`.

**Почему.** `pika` блокирующая. Внутри цикла событий один её вызов
останавливает всё остальное — в том числе отправку писем, которые уже собраны.
Протокол (AMQP 0-9-1) и брокер те же самые, меняется только клиент, поэтому
на смысл урока это не влияет: всё, чему он учит про durable, confirm,
`delivery_mode=2`, `X-Request-Id` в заголовках и Dead Letter Exchange,
реализовано и проверено.

**Последствия.** Именование в коде немного другое (`aio_pika.Message` вместо
`pika.BasicProperties`), но настройки очередей задаются теми же аргументами
AMQP, и панель управления RabbitMQ показывает ровно то же самое.

### ADR-16. Websocket-шлюз — на FastAPI, а не на сервере библиотеки websockets

**Контекст.** Урок показывает мини-чат на сервере библиотеки `websockets`.
Нашему шлюзу нужны две вещи сразу: websocket для зрителей и обычный
HTTP-эндпоинт `POST /internal/push`, которым воркер-отправщик просит доставить
сообщение.

**Решение.** Одно приложение FastAPI: `@app.websocket` для зрителей,
обычные маршруты для служебной доставки и проверки живости.

**Почему.** У `websockets` есть `process_request`, который умеет отвечать на
обычные запросы, но **не читает их тело**: служебная доставка с телом JSON
через него не проходит — соединение рвётся раньше. Пришлось бы поднимать
второй сервер на втором порту. Выяснилось это функциональным тестом, а не
рассуждением.

**Последствия.** Шлюз работает ровно в **одном** процессе: реестр открытых
соединений живёт в памяти, и с двумя воркерами зритель подключился бы к
одному, а доставка попала бы во второй. Число воркеров задано явно
(`workers=1`). Горизонтальное масштабирование шлюза потребует общей шины между
копиями (Redis pub/sub) — этого пока нет, и для учебной нагрузки не нужно.

|---|---|---|
