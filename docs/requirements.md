# Требования к сервису сбора пользовательских действий

Задание 2 модуля: из бизнес-описания вывести функциональные и нефункциональные
требования и посчитать метрики нагрузки — DAU, MAU, RPS и размер среднего
сообщения. От этих чисел считается оборудование, поэтому они здесь с расчётом,
а не одним итогом.

## Бизнес-описание, из которого всё выводится

Отделу маркетинга нужно понимать поведение зрителей: какие жанры приносят
посещения (на них тратится остаток бюджета на лицензии), что рекомендовать
конкретному человеку, что мешает досмотреть фильм. Google Analytics и Яндекс
Метрика на нашей нагрузке упираются в ограничения и не дают присоединить к
событию наши собственные данные о пользователе, поэтому сбор — свой.

Что именно нужно отслеживать:

* клики по элементам интерфейса — фильмы, трейлеры, категории;
* просмотры страниц и время, проведённое на них;
* кастомные события: смена качества видео (720p → 1080p), просмотр фильма до
  конца, использование фильтров поиска.

## Ключевые сущности и процессы

| Сущность | Что это |
|---|---|
| Событие | Факт действия: тип, время, пользователь, сессия просмотра, контекст (фильм, страница, элемент) |
| Сессия просмотра | Непрерывная работа пользователя с приложением; события одной сессии анализируются вместе |
| Пользователь | Учётная запись из сервиса авторизации; события соотносятся с ней по `user_id` |
| Поток событий | Очередь, в которую складываются принятые события до обработки |
| Аналитическое хранилище | Колоночная база, по которой аналитики считают агрегаты |

Процессы: **приём** события от клиента → **буферизация** в брокере → **перенос**
в аналитическое хранилище → **анализ** аналитиком.

## Функциональные требования

| № | Требование |
|---|---|
| ФТ-1 | Сервис принимает событие клика по элементу интерфейса: тип элемента, идентификатор элемента, страница, с которой сделан клик |
| ФТ-2 | Сервис принимает событие просмотра страницы: адрес страницы, адрес перехода и время, проведённое на странице |
| ФТ-3 | Сервис принимает кастомные события с произвольной полезной нагрузкой: смена качества видео (было/стало), просмотр до конца (доля просмотра), применение фильтров поиска (фильтры и число результатов) |
| ФТ-4 | Клиент отправляет события пачкой: копит их и отправляет одним запросом, чтобы не делать по запросу на клик |
| ФТ-5 | Каждое событие соотносится с пользователем: запрос принимается только с действующим access-токеном сервиса авторизации, `user_id` берётся из токена, а не из тела запроса |
| ФТ-6 | Событие отклоняется с машиночитаемым кодом ошибки, если не соответствует контракту; корректные события той же пачки при этом не теряются |
| ФТ-7 | Принятое событие попадает в брокер сообщений и не теряется при перезапуске сервиса приёма |
| ФТ-8 | ETL непрерывно переносит события из брокера в аналитическое хранилище |
| ФТ-9 | Схема аналитического хранилища позволяет ответить на вопросы: какие фильмы смотрят чаще всего, какие не досматривают до конца, какими фильтрами пользуются |
| ФТ-10 | Сервис отдаёт собственную документацию OpenAPI и проверку живости для оркестратора |

За рамками спринта: пользовательский контент (лайки, закладки, рецензии) —
это задание следующего спринта; анонимные события без токена; интерфейс
аналитика (аналитики работают запросами к хранилищу).

## Нефункциональные требования

Сформулированы измеримо: у каждого есть число, которое можно проверить.

| № | Требование | Значение |
|---|---|---|
| НФТ-1 | Доступность приёма событий | ≥ 99,9% в месяц (не более 43 минут недоступности) |
| НФТ-2 | Время ответа на приём пачки событий | p95 ≤ 100 мс, p99 ≤ 200 мс при пиковой нагрузке |
| НФТ-3 | Пиковая нагрузка приёма | 4 200 событий/с, около 420 HTTP-запросов/с (см. расчёт) |
| НФТ-4 | Допустимая потеря событий | ≤ 0,1% за сутки: это аналитика, а не деньги |
| НФТ-5 | Гарантия доставки | at-least-once; дубликаты допустимы, аналитика дедуплицирует по `event_id` |
| НФТ-6 | Задержка доставки события в хранилище | p95 ≤ 5 минут (аналитика не требует реального времени) |
| НФТ-7 | Время агрегирующего запроса по всем данным | ≤ 10 с |
| НФТ-8 | Срок хранения событий в аналитическом хранилище | 3 года; в брокере — 7 дней |
| НФТ-9 | Масштабируемость | горизонтальная: сервис приёма без состояния, число партиций топика ≥ 12, добавление реплики не требует изменения кода |
| НФТ-10 | Отказоустойчивость | недоступность хранилища или брокера не приводит к потере принятых событий сверх НФТ-4; ETL переживает перезапуск источника и приёмника |
| НФТ-11 | Ремонтопригодность | сбой виден в журнале с идентификатором запроса `X-Request-Id`, сквозным для всех сервисов; запрос находится в трассировке |
| НФТ-12 | Потребление памяти ETL | не растёт при непрерывной работе: за сутки прогона рост RSS ≤ 5% |
| НФТ-13 | Безопасность | события принимаются только по действующему токену; в событиях не хранится ничего персонального, кроме `user_id`; пароли и токены в журнал не попадают |
| НФТ-14 | Совместимость контракта | добавление поля в событие не ломает работающий ETL |

### Чем жертвуем: выбор по CAP

Сбор событий — **AP**: важнее принять событие и ответить клиенту, чем
гарантировать, что оно уже видно аналитику. Отсюда и at-least-once вместо
exactly-once (НФТ-5), и пятиминутная задержка доставки (НФТ-6). Для сервиса
авторизации выбор был обратный — там согласованность важнее.

## Метрики нагрузки

### Исходные допущения

Статистики по собственному сбору пока нет, поэтому числа выводятся из размера
аудитории кинотеатра и сценария использования. Все допущения перечислены —
если они изменятся, расчёт пересчитывается по той же схеме.

| Допущение | Значение | Откуда |
|---|---|---|
| MAU (уникальные пользователи за месяц) | 5 000 000 | Целевой размер аудитории кинотеатра |
| Stickiness (DAU / MAU) | 20% | Зритель заходит в среднем раз в пять дней |
| Сессий на пользователя в день | 1,5 | Вечерний просмотр плюс короткий заход выбрать фильм |
| Событий за сессию | 40 | Разложено ниже |
| Активное время суток | 16 ч (57 600 с) | Аудитория в основном в одном часовом поясе; ночью трафика почти нет |
| Событий в пачке (в пике) | 10 | Клиент копит события и отправляет не реже раза в 10 с |

Сорок событий за сессию складываются так: 10 просмотров страниц (главная,
каталог, карточки фильмов), 12 кликов по элементам, 8 событий плеера (старт,
четыре отметки прогресса, смена качества, пауза, досмотр), 4 события поиска и
фильтров, 6 прочих (закладки, переходы по рекомендациям).

### DAU и MAU

```
MAU = 5 000 000
DAU = MAU × stickiness = 5 000 000 × 0,2 = 1 000 000
```

### Событий в сутки

```
События = DAU × сессий × событий за сессию
        = 1 000 000 × 1,5 × 40 = 60 000 000 событий в сутки
```

### RPS

Нагрузка не круглосуточная: считаем по 16 активным часам.

```
Средний поток событий = 60 000 000 / 57 600 ≈ 1 042 события/с
```

Пик оцениваем по правилу Парето (80% трафика приходится на 20% времени) — так
же, как в задаче урока:

```
Пиковый поток = 60 000 000 × 0,8 / (57 600 × 0,2) ≈ 4 167 ≈ 4 200 событий/с
```

Пик выше среднего вчетверо — это вечерние часы, когда смотрят кино.

**HTTP-запросов меньше, чем событий:** клиент отправляет их пачками (ФТ-4).
При средней пачке в 10 событий:

```
Средний RPS ≈ 1 042 / 10 ≈ 104 запроса/с
Пиковый RPS ≈ 4 200 / 10 ≈ 420 запросов/с
```

Пачки — главная причина, по которой сервису приёма хватает скромного
оборудования: полторы тысячи запросов в секунду на один экземпляр Flask с
gevent достижимы, а принимать 4 200 отдельных HTTP-запросов было бы дороже.

### Размер среднего сообщения

Считаем по контракту события — JSON с общими полями и полезной нагрузкой:

| Часть события | Байт |
|---|---|
| `event_id`, `session_id`, `user_id` (три UUID с ключами) | 150 |
| `event_type`, `occurred_at` | 60 |
| Контекст: `film_id`, `page`, `element` | 150 |
| Клиент: платформа, устройство, версия приложения | 60 |
| Полезная нагрузка типа события (`payload`) | 80 |
| **Итого** | **≈ 500 байт** |

Отсюда объёмы:

```
Трафик приёма (пик)   = 4 200 × 500 Б ≈ 2,1 МБ/с ≈ 17 Мбит/с
Поток в брокер (сутки)= 60 000 000 × 500 Б ≈ 30 ГБ/сутки
Kafka, 7 дней, RF=3   = 30 ГБ × 7 × 3 ≈ 630 ГБ на кластер
ClickHouse (сутки)    ≈ 30 ГБ / 10 ≈ 3 ГБ (типизированные колонки и сжатие)
ClickHouse (3 года)   ≈ 3 ГБ × 1 095 ≈ 3,3 ТБ
```

Коэффициент сжатия 10 взят осторожно: события однородны, большинство колонок —
словарные (`event_type`, платформа) и хорошо сжимаются; фактический
коэффициент замерен в [исследовании хранилищ](../research/README.md).

### Что из этого следует для оборудования

| Компонент | Оценка |
|---|---|
| Сервис приёма | 2–3 экземпляра по 2 vCPU: пиковые 420 RPS с запасом на отказ одного экземпляра |
| Kafka | 3 брокера, топик на 12 партиций (НФТ-9), RF=3, диск 1 ТБ на брокер |
| ETL | 2–3 потребителя в группе — по одному на несколько партиций; память постоянна (НФТ-12) |
| ClickHouse | 2 узла с репликацией, диск от 4 ТБ на узел под трёхлетнее хранение |

## Проверка требований на полноту

* Каждое бизнес-требование маркетинга закрыто функциональным: клики — ФТ-1,
  просмотры страниц и время на них — ФТ-2, кастомные события — ФТ-3.
* У каждого нефункционального требования есть проверяемое число.
* Требования не противоречат друг другу: НФТ-5 (at-least-once, дубликаты
  допустимы) согласовано с ФТ-9 — дедупликация по `event_id` на стороне
  аналитических запросов.
* Требования реализуемы имеющимся стеком: брокер и колоночное хранилище
  выбраны в [ADR](architecture/README.md#adr).
