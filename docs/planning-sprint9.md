# Планирование девятого спринта: пользовательский контент, CI и наблюдаемость

Второй спринт четвёртого модуля. Сервис сбора событий и ETL уже работают
([docs/planning.md](planning.md) — декомпозиция восьмого спринта), теперь систему
нужно довести до продакшн-уровня: новое хранилище под пользовательский контент,
непрерывная интеграция и централизованные логи с мониторингом ошибок.

Шкала оценок, правила planning poker и роли — те же, что в восьмом спринте
([docs/planning.md](planning.md), разделы «Как оцениваем» и «Роли»); здесь они не
повторяются. Добавилась одна роль.

| Роль | Зона ответственности |
|---|---|
| Архитектор | Выбор хранилища, схема данных, ADR, обсуждение с наставником |
| Backend Content | Сервис пользовательского контента: API лайков, рецензий и закладок |
| Data | Исследование MongoDB против PostgreSQL, схема коллекций, индексы |
| QA/DevOps | compose, тесты, линтеры, нагрузочные прогоны |
| SRE | ELK, Sentry, CI в GitHub Actions *(новая роль спринта)* |

## Задание спринта

На ревью уходит результат пяти задач (урок «Задание и полезные ссылки»):

1. развернуть **ELK** и подключить к сервисам;
2. провести **исследование по выбору хранилища** — MongoDB против, например,
   PostgreSQL, на 10+ млн записей с нагрузочным тестированием, результаты в
   `README.md`;
3. создать **API с CRUD** для закладок, лайков и рецензий с **MongoDB** в
   качестве хранилища;
4. развернуть и подключить **Sentry**;
5. написать **CI в GitHub Actions**: линтеры, тесты через `strategy` на
   нескольких версиях Python, уведомление об успехе в Telegram.

Жёсткое нефункциональное требование всего спринта — **чтение не дольше 200 мс**:
количество лайков запрашивается при каждом открытии карточки фильма и не должно
влиять на скорость загрузки страницы.

## Доска задач

Колонки те же: **Backlog → To do → In progress → Review → Done**. Задачи заводит
`scripts/create_issues_sprint9.sh` (в репозиторий модуля и, с `--repo`, в
репозиторий спринта, где доску смотрит наставник).

Блокирующий эпик один — **E2 (исследование хранилища)**: пока хранилище не
выбрано и выбор не подтверждён замерами, писать API не на чем. Это прямо следует

## Критический путь и параллельная работа

```
E1 → E2 (блокирующий) → E3 → E4
        E5 и E6 идут параллельно с первого дня
```

* **E5 (логи) и E6 (CI) не зависят ни от чего**: и ELK, и workflow
  настраиваются на уже существующих сервисах. Их можно начинать, пока идёт
  исследование хранилища, и это единственный способ уложить спринт в срок —
  E2 упирается в генерацию 10 млн записей, которая считается часами.
* **E2 блокирует E3**: если замеры покажут, что MongoDB не вытягивает 200 мс на
  нужных сценариях, поменяется и хранилище, и модели сервиса.
* **E4 (тесты) не отделяется от E3 в конце**: unit-тесты пишутся по мере
  готовности CRUD, функциональные — после того, как сервис подключён к nginx.
* Задача 21 (единый формат журнала) трогает код сервисов, поэтому её лучше
  делать после того, как каркас нового сервиса (11) готов, — иначе формат
  придётся править дважды.

## Определение Done

Задача закрыта, если:

* код в ветке спринта (`ugc-sprint-2`), коммиты — по одной логической части;
* линтеры (`flake8`, `ruff`) и `mypy` молчат, тесты проходят;
* поведение описано в README соответствующего сервиса;
* для решений с альтернативами записан ADR;
* для задач наблюдаемости — есть живая проверка: запись видна в Kibana,
  исключение видно в Sentry, сборка видна в GitHub Actions.
