# Защита диплома «Бронирование билетов»: план доклада

Формат защиты — 20 минут: **10 минут доклад**, 10 минут вопросы. Структура —
та, что требует урок «Как организована работа в дипломном модуле».

## 1. Продуктовая проработка (≈2 мин)

* **Идея.** Связать фильмы с походами в кино: зритель становится хостом —
  предлагает фильм, место и время, — а другие зрители бронируют места и
  идут смотреть вместе.
* **Почему эта тема.** Она опирается на всё, что уже есть в кинотеатре:
  каталог (Async API и ETL), вход (Auth), письма (сервис уведомлений), — и
  добавляет то, чего не было: запись под конкуренцией, где ошибка стоит денег
  и доверия.
* **Бизнес-ценность.** Удержание (повод вернуться и привести друзей),
  сарафанное радио (каждый показ — приглашение в кинотеатр), данные о спросе
  на офлайн-показы, доверие через взаимные оценки.
  Подробнее — [requirements.md](requirements.md), раздел «Бизнес-ценность».

## 2. Планирование (≈2 мин)

* Работа индивидуальная по командному треку; роли расписаны на задачи
  (архитектор, backend, данные, интерфейс, QA).
* Методология — Waterfall с недельными контрольными точками: архитектура
  продумана к концу первой недели. План: 9 эпиков, 32 задачи, 105 SP —
  [planning.md](planning.md), доска — issues репозитория.
* **Реальный ход:** заполняется по итогам недель в разделе «Ход работ»
  плана — что сдвинулось и почему.
* **Выводы:** главный риск (перебронирование) снят исследованием до
  написания кода; самое непредсказуемое — внешние данные (обложки), его
  отделили от запуска стека файлом в репозитории.

## 3. Техническая проработка (≈3 мин)

* **Архитектура** — схема [c4-container-diploma.png](../architecture/c4-container-diploma.png):
  два новых сервиса (бронирование, интерфейс), изменения в ETL, Async API,
  админке, уведомлениях и nginx.
* **Главное решение — ADR-21:** гарантия мест в базе, условный `UPDATE` +
  `CHECK`. Слайд с таблицей исследования: проверка в коде продала 277 мест из
  10; `SERIALIZABLE` корректен, но 184 повтора; условный `UPDATE` — 10 мест,
  без повторов, p95 25 мс ([research.md](research.md)).
* **Стек с обоснованием:** PostgreSQL (транзакции, `CHECK`, частичные
  индексы), FastAPI + SQLAlchemy (единый стек с Auth и уведомлениями), Jinja2
  вместо SPA (ссылочная навигация, токены в `HttpOnly` cookie), outbox + HTTP
  к уведомлениям (независимость от их доступности).
* **Нефункциональные требования:** 300 мс — замер `scripts/load_check.py`;
  4xx с кодами вместо 5xx; деградация при отказе соседей.

## 4. Демонстрация (≈3 мин)

Подготовка: `docker compose up -d --build`, `python scripts/seed_demo.py`.

1. **Каталог** http://localhost/ — сетка обложек, жанры, поиск.
2. **Карточка фильма** — обложка, рейтинг, создатели, «Купить билет».
   Выбрать хоста (видно его рейтинг) → дату и время → места →
   «Забронировать». Показать «Мои брони» и письмо в Mailpit
   (http://localhost:8025).
3. **Гонка за места** — в терминале 30 одновременных броней на 5 мест
   (функциональный тест `test_concurrent_guests_never_oversell`): продано 5.
4. **Хост** — войти как `demo-neo`, «Моё расписание», страница показа: гости с
   рейтингом, правка места → гостям ушло письмо о переносе.
5. **Оценки** — прошедший показ: гость ставит хосту звёзды, рейтинг меняется
   в карточке фильма.
6. **Отказоустойчивость** — `docker compose stop notify-api`, бронь проходит,
   событие ждёт в outbox; `start` — письмо приходит.
7. **Наблюдаемость** — `X-Request-Id` страницы → дерево запроса в Jaeger
   (web → Async API + booking → Auth).

## 5. Вопросы, к которым готовиться

| Вопрос | Короткий ответ |
|---|---|
| Почему не Redis-счётчик мест? | Второе хранилище и рассинхронизация с бронями; база и так держит нагрузку с запасом (ADR-21) |
| Что будет при 10× нагрузке? | Запись мизерная; чтение — индекс `(film_id, starts_at)`, реплика на чтение, кеш хостов фильма |
| Почему имя хоста снимком? | 300 мс на страницу; имя меняется редко (ADR-22) |
| Как не потерять письмо? | Outbox в той же транзакции, at-least-once, постоянный `event_id` (ADR-23) |
| Почему не SPA? | Python-стек курса, ссылки, `HttpOnly` cookie, меньше каскадных запросов (ADR-24) |
| Откуда обложки и почему не у всех? | Поиск IMDb по названию, только точные совпадения; неоднозначные названия — без обложки (ADR-25) |
| Как защищены оценки от накрутки? | Только участники, только после начала, одна на пару, уникальный индекс (ADR-26) |
