# Диплом «Бронирование билетов»: исследование и выбор стека

Аналитическая работа второй недели: чем обеспечить главную гарантию
задания — не продать больше мест, чем есть у хоста, — и почему выбраны
именно эти компоненты. Решения записаны как ADR-19…ADR-26 в
[architecture.md](architecture.md).

## 1. Защита от перебронирования под конкуренцией

### Постановка

Требования (НФТ-2) и метрики нагрузки показали: записи мало (тысячи броней в
сутки), но она **сгущается** — популярный хост публикует показ на 6–10 мест,
и за секунды на него приходят десятки гостей. Ошибка в этот момент — продать
лишнее место — ровно то, что запрещает задание. Поэтому сравнивались не
хранилища вообще, а способы держать инвариант `занято ≤ мест` под
одновременными запросами.

**Стенд:** PostgreSQL 16 в Docker на ноутбуке (Apple Silicon), пул из 50
соединений — как у нескольких воркеров API. Между проверкой и записью каждая
стратегия ждёт 1 мс: так имитируется работа приложения (сеть, проверки),
именно в это окно проскакивают соперники. Ограничения `CHECK` в таблице
намеренно нет — проверяется сама стратегия.

**Скрипт:** [`booking/research/overbooking.py`](../../booking/research/overbooking.py),
сырой протокол — [`results-overbooking.log`](../../booking/research/results-overbooking.log).

### Стратегии

| Стратегия | Как устроена |
|---|---|
| `read_check` | Прочитать остаток, проверить в коде, записать новый счётчик и бронь (READ COMMITTED) |
| `count_check` | Посчитать занятые места суммой по броням, проверить, вставить бронь (READ COMMITTED) |
| `serializable` | То же, что `count_check`, на уровне SERIALIZABLE, с повтором при ошибке 40001 |
| `for_update` | `SELECT … FOR UPDATE` строки показа, проверка, `UPDATE` счётчика, бронь |
| `conditional` | Один `UPDATE … SET seats_taken = seats_taken + n WHERE seats_taken + n <= capacity RETURNING`, затем бронь |

### Результаты

**200 гостей одновременно на 10 мест**, 5 прогонов:

| Стратегия | Продано мест | Перебронирование | Повторов за прогон | p50, мс | p95, мс |
|---|---|---|---:|---:|---:|
| `read_check` | 256…277 | **5 из 5** | 0 | 122,8 | 521,9 |
| `count_check` | 62…74 | **5 из 5** | 0 | 27,0 | 49,7 |
| `serializable` | 10 | нет | **184** | 75,8 | 110,0 |
| `for_update` | 10 | нет | 0 | 69,9 | 121,5 |
| `conditional` | 10 | нет | 0 | **55,2** | **106,2** |

**20 гостей на 10 мест** (реалистичный всплеск), 20 прогонов:

| Стратегия | Продано мест | Перебронирование | Повторов за прогон | p50, мс | p95, мс |
|---|---|---|---:|---:|---:|
| `read_check` | 24…29 | **20 из 20** | 0 | 9,8 | 26,1 |
| `count_check` | 23…31 | **20 из 20** | 0 | 14,1 | 25,7 |
| `serializable` | 10 | нет | 49,3 | 26,0 | 40,1 |
| `for_update` | 10 | нет | 0 | 21,0 | 44,1 |
| `conditional` | 10 | нет | 0 | **16,4** | **25,4** |

### Выводы

1. **Проверка в коде перебронирует всегда**, и не на единицы: при 200 гостях
   `read_check` продал до 277 мест из 10. Проверка «прочитали — записали» под
   READ COMMITTED не защищает ни от чего — это главный аргумент против
   «простого» решения на защите.
2. **SERIALIZABLE корректен, но платит повторами:** 184 повтора на 200 гостей.
   Каждый повтор — лишняя транзакция; при всплеске нагрузка на базу растёт в
   разы ровно тогда, когда её и так много.
3. **`FOR UPDATE` и условный `UPDATE` корректны без повторов.** Условный
   `UPDATE` быстрее: одна команда вместо двух, и блокировка строки держится
   короче — p95 25 мс против 44 мс в реалистичном сценарии.
4. **Выбран условный `UPDATE` + `CHECK` в таблице** (ADR-21). PostgreSQL сам
   ждёт блокировку строки и перепроверяет условие на свежей версии
   (EvalPlanQual), а `CHECK (seats_taken <= capacity)` не даст записать
   перебронирование даже при ошибке в коде.

Ту же гарантию сервис проверяет функциональным тестом на настоящей базе:
30 одновременных броней на 5 мест — продано ровно 5.

**Проверка сторожей.** Тест нарочно запускался на сервисе, из `UPDATE`
которого убрано условие `seats_taken + n <= capacity`. Продано всё равно
ровно 5 мест: их удержал `CHECK` в таблице, — но ответом на лишнюю бронь был
не `409 not_enough_seats`, а сбой. Поэтому нарушение `CHECK` при занятии мест
теперь переводится в обычный отказ «мест нет»: два независимых рубежа, и ни
один не превращается в 5xx.

## 2. Выбор стека

### Хранилище броней — PostgreSQL 16 (ADR-20)

| Критерий | PostgreSQL | MongoDB (как в сервисе контента) | Redis |
|---|---|---|---|
| Атомарность «счётчик + бронь + событие» | транзакция | только на наборе реплик, многодокументная транзакция | `MULTI`/Lua, но брони и outbox всё равно хранить где-то ещё |
| Инвариант `занято ≤ мест` в самом хранилище | `CHECK` | нет `CHECK` по двум полям | нет |
| «Одна активная бронь гостя» | частичный уникальный индекс | частичный уникальный индекс | вручную |
| Объём (≈7 млн строк за 3 года) | с запасом на одном узле | с запасом | не для долговременного хранения |
| Уже в стеке | да (Auth, уведомления, каталог) | да | да |
| Опыт команды | Auth, уведомления | контент | кеши |

Объём записи мизерный, шардирование не нужно, а все инварианты брони
выражаются средствами реляционной базы. PostgreSQL — та же версия, что у
остальных баз стека: одна версия на стек, одни и те же приёмы эксплуатации.

### Сервис — FastAPI + SQLAlchemy 2 (asyncpg) + Alembic

Тот же стек, что у сервисов авторизации и уведомлений: асинхронный ввод-вывод
(время ответа определяют походы в базу и соседние сервисы, а не процессор),
OpenAPI из коробки, слоистая архитектура и тесты на хранилищах в памяти
переносятся без изменений. Alembic — потому что схема меняется миграциями, и
`alembic check` в проверках ловит расхождение моделей с базой.

### Интерфейс — FastAPI + Jinja2 (ADR-24)

| Критерий | Серверные страницы (FastAPI + Jinja2) | SPA (React/Vue) |
|---|---|---|
| Язык и стек | Python, как весь курс | TypeScript, сборка Node.js |
| Токены | `HttpOnly` cookie, JavaScript их не видит | обычно `localStorage` или отдельный BFF |
| Навигация ссылками (требование к диплому) | естественная | маршрутизатор SPA |
| Время страницы | параллельные запросы к API на сервере, одна загрузка | каскад запросов из браузера |
| Тесты и CI | pytest, тот же CI | отдельный стек тестов |

### Связь с уведомлениями — outbox + HTTP API (ADR-23)

Прямая публикация в RabbitMQ сервиса уведомлений привязала бы сервис
бронирования к внутреннему формату чужих очередей. Контракт сервиса
уведомлений — его API с `event_id` для идемпотентности; outbox делает
отправку независимой от его доступности. Проверено живьём на стенде: при
остановленном `notify-api` бронь отвечает 201, два события ждут в outbox с
причиной в `last_error` и уходят после подъёма; то же — функциональным тестом.

### Обложки — ссылка в каталоге, поиск IMDb (ADR-25)

Официальные API (OMDb, TMDB) требуют ключ и регистрацию; Кинопоиск без входа
отправляет на авторизацию Яндекса, а его API (kinopoiskapiunofficial.tech,
api.kinopoisk.dev) отвечают 401 без ключа. Поиск IMDb по названию без ключа дал
обложки 729 фильмам из 999: берётся только точное совпадение названия, а 40
названий, под которыми в каталоге несколько разных фильмов, пропускаются —
чужая обложка хуже заглушки. Картинки не хранятся — только ссылки; запуск стека от сети не
зависит, потому что ссылки лежат файлом в репозитории.
