# Онлайн-кинотеатр: Async API, авторизация, админка и сбор действий

Четыре сервиса онлайн-кинотеатра за общим nginx:

* **Async API** — точка входа для клиентов каталога: отдаёт фильмы, жанры и
  персоны из Elasticsearch и кеширует ответы в Redis;
* **сервис авторизации** ([auth/](auth/README.md)) — регистрация, вход по
  логину и паролю или через соцсеть (Яндекс, Google) с парой JWT-токенов,
  выход (в том числе из остальных устройств), личный кабинет с историей входов
  и связанными аккаунтами, роли и проверка прав.
  Архитектура — [auth/docs/architecture.md](auth/docs/architecture.md);
* **админка каталога** ([admin_panel/](admin_panel/README.md)) — Django-админка,
  через которую редакторы ведут фильмы, жанры и персоны. Сотрудники входят в
  неё учётной записью кинотеатра: вход проверяет сервис авторизации, отдельного
  пароля у админки нет;
* **сервис сбора пользовательских действий** ([ugc/](ugc/README.md)) —
  принимает клики, просмотры страниц и события плеера и складывает их в Kafka,
  откуда [ETL](ugc_etl/README.md) непрерывно переносит их в ClickHouse для
  аналитиков. Требования — [docs/requirements.md](docs/requirements.md),
  схемы AS IS и TO BE — [docs/architecture/](docs/architecture/README.md).

Роли ограничивают доступ к категориям фильмов: фильмы, вышедшие менее трёх лет
назад, ETL помечает `access_level=subscription`, и Async API отдаёт их только
роли `subscribers` с правом `films.subscription` — подробности в разделе
[«Доступ к фильмам»](#доступ-к-фильмам). Роль `staff` с правом `admin.access`
пускает сотрудника в админку.

## Архитектура

```
                       ┌─ /api/   ─► api ──┬─► redis (кеш)
                       │                   ├─► elasticsearch ◄── etl ◄──┐
                       │                   └─► auth   (право films.subscription)
клиент ──► nginx :80 ──┼─ /auth/  ─► auth ─┬─► auth-redis    (сессии, кеш прав)
                       │                   └─► auth-postgres (пользователи, роли, история входов)
                       │                                                │
                       ├─ /admin/ ─► django-admin ─┬─► postgres (каталог фильмов)
                       │                           └─► auth   (вход сотрудника)
                       │
                       └─ /ugc/   ─► ugc ──► kafka ──► ugc-etl ──► clickhouse ──► аналитик
```

У каждого сервиса свои хранилища; общие у них только nginx и сервис
авторизации, к которому ходят и Async API (право на подписочные фильмы), и
админка (вход сотрудников). Async API только читает индексы `movies`, `genres`
и `persons` — их заполняет ETL из базы фильмов, ту же базу правит админка, так
что правка редактора доезжает до выдачи API через ETL и Elasticsearch.

ETL живёт в своём репозитории
[new_admin_panel_sprint_3](https://github.com/storublev/new_admin_panel_sprint_3)
и в этот репозиторий не копируется. `docker-compose.yml` собирает ETL из соседнего
каталога (переменная `ETL_PROJECT_PATH`), чтобы все сервисы поднимались одной командой.

| Сервис | Назначение |
|---|---|
| `nginx` | Входная точка: `/api/` — в Async API, `/auth/` — в сервис авторизации, `/admin/` и `/static/` — в админку, пулы keepalive-соединений |
| `api` | FastAPI + uvicorn (uvloop, httptools), несколько процессов-воркеров |
| `redis` | Кеш ответов API, LRU-вытеснение, без персистентности |
| `elasticsearch` | Хранилище для чтения и полнотекстового поиска |
| `postgres` | Каталог фильмов: схема `content` из дампа ETL, схема `public` — таблицы админки |
| `etl` | Перенос данных PostgreSQL → Elasticsearch с отслеживанием изменений и меткой доступа фильмов |
| `auth` | Сервис авторизации: FastAPI + uvicorn, без состояния |
| `auth-postgres` | Пользователи, роли, история входов — отдельно от данных о фильмах |
| `auth-redis` | Сессии и кеш прав: без вытеснения ключей, с журналом AOF |
| `auth-migrations` | Одноразовый контейнер с миграциями Alembic |
| `django-admin` | Админка каталога: Django + gunicorn |
| `django-admin-migrations` | Одноразовый контейнер: миграции админки и сборка статики в общий том |
| `ugc` | Сервис сбора пользовательских действий: Flask + gunicorn с воркерами gevent |
| `kafka` | Брокер событий в режиме KRaft, топик `ugc.events` |
| `kafka-init` | Одноразовый контейнер: заводит топик с нужным числом партиций |
| `ugc-etl` | Непрерывный перенос событий из Kafka в ClickHouse с повторами, прерывателем и наблюдением за памятью |
| `clickhouse` | Аналитическое хранилище событий: сырые события и витрина по фильмам |
| `jaeger` | Сбор спанов трассировки и дерево запроса по ним; интерфейс — http://localhost:16686 |

## Запуск

Нужны Docker и Docker Compose v2, а рядом с этим репозиторием — клон ETL:

```bash
git clone git@github.com:storublev/new_admin_panel_sprint_3.git ../new_admin_panel_sprint_3
cp .env.example .env
```

В `.env` задайте секреты — без них docker-compose не запустится:
`AUTH_POSTGRES_PASSWORD`, `AUTH_JWT_SECRET_KEY` и `DJANGO_SECRET_KEY` (ключи —
не короче 32 символов, например
`python3 -c "import secrets; print(secrets.token_urlsafe(48))"`).
При необходимости поправьте `ETL_PROJECT_PATH` и порты. Затем:

```bash
docker compose up -d --build
docker compose exec auth python cli.py createsuperuser --login admin
```

После старта ETL загружает данные в Elasticsearch (при первом запуске — около
минуты), дальше подхватывает изменения в PostgreSQL. Миграции сервиса
авторизации применяет контейнер `auth-migrations`, миграции админки и сборку её
статики — `django-admin-migrations`; оба отрабатывают до запуска своих сервисов.

* Документация Async API: http://localhost/api/openapi
* Документация сервиса авторизации: http://localhost/auth/api/openapi
* Документация сервиса сбора событий: http://localhost/ugc/api/openapi
* Админка каталога: http://localhost/admin/
* Трассировка (Jaeger): http://localhost:16686
* Спецификации: http://localhost/api/openapi.json, http://localhost/auth/api/openapi.json,
  http://localhost/ugc/api/openapi.json

События, принятые сервисом сбора, доезжают до ClickHouse за несколько секунд;
посмотреть, что доехало:

```bash
docker compose exec clickhouse clickhouse-client --query \
    "SELECT event_type, count() FROM ugc.events GROUP BY event_type"
```

В документации для клиентов описаны пагинация, ошибки (404, 422, 503 с моделью
`ErrorSchema`), назначение каждого эндпоинта и тега, поля ответов с примерами.
Команды, тесты и настройки сервиса авторизации — в [auth/README.md](auth/README.md),
админки — в [admin_panel/README.md](admin_panel/README.md).

Учётных записей после запуска нет: их заводят в сервисе авторизации, а не в
админке. Суперпользователь из команды выше (`createsuperuser`) входит в админку
сразу. Обычного сотрудника надо зарегистрировать и выдать ему роль `staff` с
правом `admin.access`:

```bash
# регистрация
curl -s -X POST http://localhost/auth/api/v1/signup -H 'Content-Type: application/json' \
    -d '{"login":"editor","password":"editor-password"}'
```

Команды назначения роли и отзыва доступа — в
[admin_panel/README.md](admin_panel/README.md#как-завести-сотрудника).

## Функциональные тесты Async API

Тесты сервиса авторизации описаны в [auth/README.md](auth/README.md#тесты).

Тесты проверяют API снаружи, через HTTP: сами наполняют Elasticsearch, шлют
запросы и сверяют ответы. Код приложения они не импортируют, схемы индексов —
копия схем ETL (`tests/functional/testdata/es_mapping.py`). Стек: pytest,
pytest-asyncio, aiohttp.

Доступ к подписочным фильмам проверяется против **настоящего** сервиса
авторизации, а не заглушки: тесты регистрируют в нём пользователей и выдают
роль `subscribers`, поэтому проверяется его реальный контракт. Поведение API
при недоступности сервиса авторизации проверяют unit-тесты — там сбои
воспроизводятся точнее, чем гашением контейнера.

Запуск в изолированном окружении — API, Elasticsearch, Redis, сервис
авторизации со своими хранилищами и контейнер с тестами поднимаются отдельным
docker-compose; ETL и база фильмов не нужны:

```bash
docker compose -f tests/functional/docker-compose.yml up --build \
    --abort-on-container-exit --exit-code-from tests
docker compose -f tests/functional/docker-compose.yml down
```

Код выхода команды — результат тестов. Перед запуском контейнер тестов ждёт,
пока Elasticsearch и Redis начнут отвечать (`tests/functional/utils/wait_for_*.py`):
`depends_on` гарантирует только запуск процесса, а не готовность сервиса.

Локально, например из IDE с отладчиком: docker-compose тестов пробрасывает на
localhost порты API (8000), Elasticsearch (9200), Redis (6379) и сервиса
авторизации (8001), а настройки
тестов по умолчанию смотрят туда же.

```bash
docker compose -f tests/functional/docker-compose.yml up -d --build --wait api
pip install -r tests/functional/requirements.txt
pytest tests/functional                      # или: pytest tests/functional -k search
```

Порты меняются переменными `TEST_API_PORT`, `TEST_ELASTIC_PORT`,
`TEST_REDIS_PORT`, `TEST_AUTH_PORT`, адреса для тестов — `SERVICE_URL`,
`ELASTIC_URL`, `REDIS_HOST`, `REDIS_PORT`, `AUTH_URL`. **Тесты пересоздают индексы `movies`, `genres`,
`persons` и очищают Redis — не направляйте их на рабочие хранилища.**

```
tests/functional/
├── conftest.py            # фикстуры: клиенты на сессию, очистка перед тестом, запись в ES, запрос к API
├── docker-compose.yml     # API, Elasticsearch, Redis и тесты
├── Dockerfile             # образ с тестами; entrypoint.sh ждёт хранилища и запускает pytest
├── pytest.ini
├── requirements.txt
├── settings.py            # адреса API и хранилищ
├── src/                   # тесты по эндпоинтам
├── testdata/              # схемы индексов, фабрики документов, граничные значения параметров
└── utils/                 # ожидание Elasticsearch и Redis, вспомогательный код
```

Скорость: клиенты Elasticsearch, Redis и HTTP-сессия создаются один раз на
сессию, индексы — тоже; перед каждым тестом из индексов удаляются документы и
сбрасывается кеш. Документы пишутся с `refresh`, поэтому тестам не нужны паузы.

### Unit-тесты

Проверяют контракты слоя хранилищ и бизнес-логику без Docker и внешних
сервисов: как адаптер Elasticsearch строит запрос, как сервисы переживают сбой
кеша, как разбираются ответы сервиса авторизации, что делает прерыватель и
кому какие фильмы видны.

```bash
pip install -r tests/unit/requirements.txt
pytest tests/unit
```

Модульные тесты админки (бэкенд аутентификации, клиент сервиса авторизации,
прерыватель, перепроверка доступа) — в
[admin_panel/README.md](admin_panel/README.md#тесты).

## Эндпоинты Async API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/films?sort=-imdb_rating&genre=<uuid>` | Популярные фильмы, фильтр по жанру (он же — похожие фильмы) |
| `GET /api/v1/films/search?query=<строка>` | Поиск по названию и описанию фильмов |
| `GET /api/v1/films/<uuid>` | Полная информация по фильму |
| `GET /api/v1/genres` | Список жанров |
| `GET /api/v1/genres/<uuid>` | Данные по жанру |
| `GET /api/v1/persons` | Список персон |
| `GET /api/v1/persons/search?query=<строка>` | Поиск по персонам |
| `GET /api/v1/persons/<uuid>` | Данные по персоне и её роли в фильмах |
| `GET /api/v1/persons/<uuid>/film` | Фильмы персоны |

### Доступ к фильмам

Жанры и персоны открыты всем. Фильмы делятся на публичные и доступные по
подписке: ETL помечает фильм, вышедший менее трёх лет назад,
`access_level=subscription`, и смотреть такие фильмы может только пользователь
с правом `films.subscription` (роль `subscribers`).

Токен передаётся заголовком `Authorization: Bearer <access-токен>` из
`POST /auth/api/v1/login`. Без него запрос анонимный: доступны только публичные
фильмы. Async API проверяет право в сервисе авторизации на каждый запрос с
токеном, с `fresh=true` — минуя кеш прав, поэтому отозванная подписка
закрывает доступ сразу. Анонимный запрос в сервис авторизации не идёт.

| Кто | Списки и поиск | Карточка подписочного фильма |
|---|---|---|
| Аноним или пользователь без подписки | только публичные фильмы | 403 |
| Подписчик | публичные и подписочные | 200 |
| Любой, пока сервис авторизации недоступен | только публичные фильмы | 503 |

**Изящная деградация.** Сервис авторизации — самый нагруженный на сайте, и его
отказ не должен ронять выдачу каталога. У запроса к нему явные таймауты,
повторяется только обрыв соединения (таймаут ответа — нет: сервис уже занят
запросом), а пять сбоев подряд размыкают прерыватель на 30 секунд, и запросы
перестают уходить вовсе. Без ответа сервиса списки и поиск отдают публичные
фильмы, как анонимному пользователю, а карточка подписочного фильма отвечает
503 `subscription cannot be verified now` — подписку не подтвердить, но и
отказывать в ней неверно.

Общие параметры списков:

* `page_number` (с 1, по умолчанию 1) и `page_size` (1–100, по умолчанию 50).
  Произведение `page_number * page_size` не больше 10 000 — дальше Elasticsearch
  не отдаёт результаты (`index.max_result_window`), на такой запрос API вернёт 422;
* `sort` — `-imdb_rating` (по умолчанию) или `imdb_rating`;
* поиск сортируется по релевантности.

Несуществующий `uuid` — 404, невалидный — 422. Если Elasticsearch недоступен
(нет соединения, истёк таймаут) или нужный индекс ещё не создан, API отвечает
503 `service temporarily unavailable`, а причину пишет в журнал.

### Решения по несостыковкам ТЗ

* **Косая черта в конце пути.** В ТЗ встречаются оба варианта (`/films/<uuid>/` и
  `/persons/<uuid>`). Маршруты объявлены без слеша, а `TrailingSlashMiddleware`
  отбрасывает слеш в конце — оба варианта работают без 307-редиректа.
* **`/persons/<uuid>/film`** — оставлено в единственном числе, как в ТЗ: на этот
  путь ориентируются клиенты.
* **Список персон `GET /api/v1/persons`** в ТЗ не описан; добавлен во втором
  спринте — функциональные тесты требуют «вывести всех людей». Сортировка по имени.
* **Поле `genre`** в ответе по фильму — тоже как в ТЗ, хотя это список.
* **`imdb_rating`** в ответах — число, а не строка `"float"` из схем ТЗ.
* **Жанр** содержит `name` (его возвращает API) и `description` (в индексе).
* Примеры из ТЗ с невалидными UUID (`g`, кириллическая `с`) и повторяющимися
  идентификаторами не годятся для фикстур.

## Производительность Async API

* **C10k.** Нагрузка I/O-bound, поэтому весь путь запроса асинхронный:
  `AsyncElasticsearch`, `redis.asyncio`, uvicorn с uvloop. Один процесс
  обслуживает тысячи соединений без пула потоков; число процессов задаёт
  `API_WORKERS`. Перед API стоит nginx с `worker_connections 10240` и пулом
  keepalive-соединений к upstream.
* **Кеш.** Ответы кешируются в Redis по набору параметров запроса: карточки по
  `uuid` и страницы списков — по хешу запроса к хранилищу. Время жизни —
  `CACHE_EXPIRE_IN_SECONDS` (5 минут). Если Redis недоступен, запрос идёт
  напрямую в Elasticsearch, API продолжает работать. Запись кеша, которая не
  проходит проверку модели (повреждена или осталась от прошлой версии), считается
  отсутствующей: данные читаются из Elasticsearch, и запись перезаписывается.
* Для списков из Elasticsearch запрашиваются только нужные поля (`_source`),
  подсчёт общего числа совпадений отключён.

### Сбои внешних сервисов: exponential backoff

* **Elasticsearch.** Если Elasticsearch отказывает в соединении (перезапуск,
  сбой сети), `ElasticStorage` повторяет запрос с экспоненциальной паузой:
  0,1 → 0,2 → 0,4 … с, не больше 1 с, со случайным разбросом, чтобы воркеры не
  повторяли запросы одновременно. Через `ELASTIC_BACKOFF_MAX_TIME` (3 с) повторы
  прекращаются и API отвечает 503. Таймаут (`ELASTIC_REQUEST_TIMEOUT`, 2 с) не
  повторяется: зависший Elasticsearch вряд ли ответит на вторую попытку, а
  каждая заняла бы ещё столько же. Встроенные повторы клиента отключены — они
  идут без паузы и умножали бы число попыток.
* **Redis.** Кеш не должен задерживать ответ, поэтому при обрыве соединения —
  один повтор с паузой в сотые доли секунды (этого хватает, чтобы
  переподключиться после перезапуска Redis), таймауты не повторяются. Если
  Redis недоступен, запрос идёт в Elasticsearch.
* **Функциональные тесты** ждут Elasticsearch и Redis тоже с экспоненциальной
  паузой (библиотека `backoff`).

Проверено вручную на окружении тестов: при остановленном Elasticsearch API
отвечает 503 через 3 с после 12 попыток; если Elasticsearch поднимается, пока
идут повторы, запрос проходит; при остановленном Redis ответы приходят за
15–30 мс, после его перезапуска кеш снова работает.

## Структура Async API

```
src/
├── main.py              # приложение, lifespan с клиентами ES и Redis
├── api/dependencies.py  # сборка сервисов: какие хранилища и кеш они получают
├── api/v1/              # роутеры, параметры запросов, схемы ответов
├── core/                # настройки, логирование, middleware
├── db/                  # клиенты Elasticsearch и Redis
├── models/              # модели документов Elasticsearch
├── services/            # бизнес-логика: базовый сервис с кешем, фильмы, жанры, персоны
└── storage/             # интерфейсы хранилища документов и кеша, реализации на Elasticsearch и Redis
```

Общая логика чтения по `id`, поиска, пагинации и кеширования — в
`services/base.py`; сервисы сущностей описывают только свои запросы.

Сервисы не зависят от Elasticsearch: запрос они описывают нейтральной
структурой `SearchRequest` (поля, пагинация, полнотекстовый поиск, связь с
жанром или персоной, сортировка) и передают хранилищу `DocumentStorage`.
Перевод в запрос Elasticsearch и обработка его сбоев — в `storage/elastic.py`.
Другое хранилище подключается новой реализацией `DocumentStorage` без правок
в сервисах. Синтаксис конкретного хранилища в сервисы не попадает: например,
вес поля поиска задаётся значением — `SearchField('title', weight=3)`, а в
строку `title^3` его переводит адаптер Elasticsearch.

С кешем так же: сервисы работают с `ModelCache` (`services/cache.py`), который
сериализует модели, проверяет записи и задаёт время жизни, а хранит данные
через интерфейс `Cache`. Реализация на Redis — `storage/redis.py`.

Контракт `Cache` для всех реализаций: при сбое своего хранилища методы
поднимают `CacheUnavailableError` и только его. Что делать при сбое, решает
`ModelCache` — в одном месте для любой реализации: чтение становится промахом,
запись пропускается, запрос обслуживается из Elasticsearch. Поэтому замена
Redis на другой кеш не меняет поведения API при его недоступности.

Конкретные реализации выбираются в одном месте — `api/dependencies.py`
(Composition Root): оттуда эндпоинты получают готовые сервисы через `Depends`.
Модули сервисов содержат только бизнес-логику и не импортируют ни FastAPI,
ни клиенты Elasticsearch и Redis.

  ([docs/architecture/](docs/architecture/README.md)).
* **Сервис сбора событий** ([ugc/](ugc/README.md)) — Flask с воркерами gevent.

* **Пользователь — из токена, а не из тела запроса.** Подпись access-токена
  проверяется на месте, общим с сервисом авторизации секретом: сетевой вызов
  на каждое событие сделал бы сервис авторизации узким местом.

  не нужен.
* **Маршрут `/ugc/` в nginx** со своим пределом частоты запросов по адресу:
  поток событий на порядок плотнее каталожного.
* **ETL событий** ([ugc_etl/](ugc_etl/README.md)) — непрерывно переносит
  события из Kafka в ClickHouse пачками. Смещения подтверждаются только после
  успешной вставки, поэтому падение приводит к повтору пачки, а не к её потере;
  повторы схлопывает `ReplacingMergeTree`. Недоступность хранилища переживается
  повторами с паузой и прерывателем — события ждут в брокере. За памятью
  следит сторож: ETL работает неделями, и утечка в нём видна не падением, а
  ростом RSS.
* **Схема аналитического хранилища**: сырые события с TTL в три года и витрина
  `film_daily`, которую наполняет материализованное представление, — по ней
  считаются самые просматриваемые и недосмотренные фильмы.
* **Исследование хранилищ** ([research/](research/README.md)): 10 000 000
  сгенерированных событий, замеры вставки, чтения и чтения под нагрузкой.
  ClickHouse принимает 243 700 строк/с, хранит событие в 31 байте и отвечает
  на аналитические запросы за сотые доли секунды. Vertica замерить не вышло —
  с версии 26.1 у неё нет бесплатной редакции; подробности и решение — в
  ADR-5.

### Спринт 7 — исправления по ревью

* **Смена пароля отменяет начатую привязку соцсети.** Вместе со `state`
  запоминается сессия и версия учётных данных; перед привязкой сервис
  проверяет, что вход, с которого её начали, ещё действует, иначе — 401
  `social_link_expired`. Раньше завладевший токеном мог закончить привязку
  уже после смены пароля и завести себе собственный способ входить.
* **Проверки пароля в личном кабинете ограничены** по учётной записи и по IP,
  попытка засчитывается до проверки пароля. Смена логина и смена пароля делят
  один счётчик, верный пароль его обнуляет; первый рубеж — `limit_req` в nginx
  и на этих эндпоинтах. Раньше через кабинет можно было перебирать пароль с
  украденным токеном в обход лимитов входа.
* **Открепление соцсети — одна операция с блокировкой строки пользователя:**
  оставшиеся способы войти считаются и связь удаляется вместе. Раньше два
  одновременных запроса могли снять две последние соцсети — каждый видел, что
  другая ещё на месте, — и владелец терял доступ к аккаунту.
* **Админка перепроверяет доступ сотрудника, пока он работает.** Вход больше
  не закрывает сессию в сервисе авторизации, а сохраняет её токены у записи
  сотрудника (миграция `0002`): раз в минуту middleware предъявляет их снова и
  спрашивает право по базе, обновляя пару по `refresh`, когда access-токен
  истёк. Снятое право, смена пароля и «выйти из остальных сессий» закрывают и
  сессию админки; выход из админки закрывает сессию в сервисе. Пока сервис
  недоступен, действует последняя удачная проверка, но не дольше пяти минут.
* **Отключённый сотрудник не возвращается в админку.** Признак «активен»
  принадлежит админке: вход его больше не выставляет у существующей записи, а
  отключённому сотруднику отказывает, даже если право в сервисе у него есть.

### Спринт 7 — трассировка и партицирование

* **Сквозной идентификатор запроса.** nginx выдаёт его каждому входящему
  запросу и передаёт заголовком `X-Request-Id`, перезаписывая присланный
  клиентом. Он попадает в access-лог nginx, в каждую запись журнала сервисов,
  в тег спана `http.request_id` и в ответ клиенту; каждый сервис передаёт его
  дальше, в исходящие вызовы. Запрос без заголовка отклоняется с 400 — он
  пришёл мимо шлюза и не найдётся ни в журналах, ни в Jaeger.
* **Трассировка** на OpenTelemetry, спаны уходят в Jaeger по OTLP. Запросы
  Async API к сервису авторизации инструментированы и уносят контекст
  заголовком `traceparent`, поэтому в Jaeger видно дерево из обоих сервисов.
  Без адреса коллектора трассировка выключается.
* **История входов разбита на месячные секции** (RANGE по `created_at`,
  миграция `0007`): год истории удаляется `DROP TABLE` одной секции, свежие
  секции невелики и целиком помещаются в память. Секции будущих месяцев
  создаёт `cli.py create-login-partitions`, пропущенный месяц страхует секция
  по умолчанию.

### Спринт 7 — вход через соцсети

* Вход и регистрация через Яндекс и Google по OAuth 2.0 — сторона потребителя
  на Authlib, Authorization Code Flow. Своего сервера OAuth и фронтенда нет:
  `GET /oauth/{provider}/login` уводит к поставщику, `…/callback` меняет код на
  пару токенов. Перехваченный код без `client_secret` бесполезен.
* Переход и возврат связывает `state` — одноразовый, с коротким сроком жизни в
  Redis; без него чужой ответ поставщика привязал бы к жертве чужой аккаунт.
  К кому привязывать аккаунт, решается в начале входа, а не на возврате.
* Пользователь опознаётся только по паре (поставщик, `social_id`), таблица
  `social_accounts` (миграция `0006`). По email — нельзя: его меняют и не
  всегда подтверждают.
* Первый вход заводит учётную запись без пароля (`password_hash` стал
  необязательным). Войти в неё по паролю нельзя, и время ответа этого не
  выдаёт; первый пароль владелец задаёт в личном кабинете без подтверждения
  текущим.
* Личный кабинет показывает связанные аккаунты и позволяет их **откреплять**.
  Последний способ войти открепить нельзя — иначе доступ к учётной записи
  был бы потерян.
* Поставщик включается, только когда заданы оба его ключа; без них его
  эндпоинты отвечают 404, а остальной вход работает как прежде.

### Спринт 7 — интеграция сервисов

* Async API проверяет доступ к фильмам в сервисе авторизации: фильмы с меткой
  `access_level=subscription` видит только пользователь с правом
  `films.subscription`. Списки и поиск закрытые фильмы не показывают, карточка
  отвечает 403. Право спрашивается на каждый запрос с токеном и мимо кеша прав
  (`fresh=true`), потому что access-токен действует, пока жива сессия, и сам по
  себе не говорит, не отозвана ли подписка.
* Отказ сервиса авторизации не роняет каталог: явные таймауты, повтор только
  обрыва соединения, прерыватель на пять сбоев подряд, а без ответа — выдача
  публичных фильмов и 503 вместо 403 на подписочный фильм.
* Функциональные тесты Async API поднимают настоящий сервис авторизации, а не
  заглушку: 187 тестов вместо 174.
* Линтеры `flake8` и `ruff` настроены и для Async API — раньше конфигурации
  были только у сервиса авторизации.

### Спринт 6 — исправления по ревью

* Ограничение частоты входа и регистрации: счётчики попыток в Redis, общие для
  всех процессов, со скользящим окном — вход по IP и по логину, регистрация по
  IP; ответ 429 `too_many_requests` с `Retry-After`, сверх лимита Argon2 не
  считается. Первый рубеж — `limit_req` в nginx; nginx перезаписывает
  `X-Forwarded-For`, чтобы лимит по IP нельзя было обойти подменой адреса.
* Смена пароля закрывает остальные сессии независимо от Redis: версия учётных
  данных меняется в одной транзакции с паролем, и сессии с прежней версией не
  действуют (миграция `0003`).
* Отзыв и изменение ролей не оставляют прежние права в кеше при сбое Redis:
  задание на сброс кеша пишется в той же транзакции и повторяется фоновой
  задачей (миграция `0004`); право `access.manage` проверяется по базе, а
  `GET /access/check?fresh=true` позволяет так проверить любое право.
* Сессии пользователя — в сортированном множестве со сроком окончания:
  истёкшие удаляются при входе и обновлении токенов, число сессий ограничено
  (`AUTH_MAX_SESSIONS_PER_USER`).
* Время жизни в переменных окружения можно задавать числом секунд, как и
  было описано (раньше принимался только формат ISO 8601).
* После обновления все пользователи входят заново один раз: сессии, открытые
  до появления версии учётных данных, не принимаются.

### Спринт 6 — сервис авторизации

* Описана архитектура сервиса: компоненты, модель доступа (RBAC), схема
  данных, токены и сессии, обработка ошибок — `auth/docs/architecture.md`,
  спецификация `auth/docs/openapi.json`.
* Регистрация, вход по логину и паролю с выдачей пары токенов (JWT access +
  одноразовый refresh), обновление пары, выход.
* «Выйти из остальных устройств» без хранения access-токенов: токен действует,
  пока жива его сессия в Redis.
* Защита от повторного использования refresh-токена: сессия закрывается целиком.
* Личный кабинет: данные пользователя с ролями, смена логина и пароля
  (подтверждаются текущим паролем; смена пароля закрывает остальные сессии),
  история входов с устройством и IP.
* CRUD ролей, назначение и отзыв ролей, проверка права пользователя с кешем в
  Redis; изменения ролей действуют сразу.
* Суперпользователь (консольная команда `createsuperuser`) — ему разрешено всё;
  анонимному пользователю доступно только то, что правом не ограничено.
* Роль `subscribers` с правом `films.subscription`; ETL помечает фильмы,
  вышедшие менее трёх лет назад, `access_level=subscription` и раз в сутки
  снимает метку с тех, что перестали быть новинками.
* Пароли — Argon2id; ошибки с машиночитаемыми кодами (`token_expired`,
  `token_invalid`, `token_revoked`, ...); 503 при недоступности хранилищ.
* Unit- и функциональные тесты на каждый ответ каждого эндпоинта, линтеры
  flake8 и ruff.
