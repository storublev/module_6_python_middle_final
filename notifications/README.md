# Сервис уведомлений

Рассылает письма и мгновенные уведомления зрителям онлайн-кинотеатра:
приветственное письмо после регистрации, подборку недели всем, персональные
итоги месяца, сообщения о новых сериях и ручные рассылки менеджера.

Проект и обоснование решений — [docs/architecture/notifications.md](../docs/architecture/notifications.md),
требования и метрики нагрузки — [docs/requirements-sprint10.md](../docs/requirements-sprint10.md).

## Как это работает

```
источник события ─┐
генератор (cron) ─┼─► API /notify/api/v1/events ─► RabbitMQ ─► планировщик ─► сборщик ─► отправитель ─► SMTP
админ-панель  ────┘                                                                   └─► websocket-шлюз
```

**API рассылкой не занимается.** Он проверяет контракт, отбивает повтор по
`event_id` и кладёт сообщение в очередь — и отвечает сразу, не дожидаясь, пока
письма разойдутся. Всё остальное делают воркеры, и это не украшение: событие
«вышла новая серия» касается тысяч зрителей, а http-запрос администратора,
который эту серию опубликовал, висеть минутами не должен.

Три воркера вместо одного, потому что у них разные узкие места:

| Воркер | Что делает | Обо что спотыкается |
|---|---|---|
| **планировщик** (`plan`) | разворачивает адресацию в получателей, отсеивает отписавшихся и тех, кому уже писали об этой версии данных, режет на пачки | своя база |
| **сборщик** (`render`) | берёт контакты **пачкой** из сервиса авторизации, проверяет актуальность, собирает письмо по шаблону | чужие сервисы |
| **отправитель** (`send`) | занимает ключ идемпотентности и отправляет через канал | почтовый сервер |

Отказ почтового сервера не мешает собирать письма впрок, а отказ сервиса
авторизации не мешает отправлять уже собранные.

### Гибридная подготовка данных

Главное правило, из которого следует остальное:

> **в сообщение едут идентификаторы и версия, а не содержимое.** Тяжёлая
> статистика считается витриной до очереди, а адрес, имя и часовой пояс
> получателя сборщик добирает сам, одним запросом на пачку.

Поэтому воркеру и не приходит email и ФИО — их у события нет. Он идёт за ними
в справочник контактов сервиса авторизации
(`POST /auth/api/v1/users/contacts`), опознаваясь служебным секретом.

### Что защищает зрителя от лишних писем

| Правило | Как сделано |
|---|---|
| Ни одного дубля | `event_id` на входе + ключ идемпотентности `(событие, зритель, канал, версия)` перед отправкой |
| Об одном и том же не пишем дважды | в записи уведомления хранится версия данных, о которой сообщили |
| Ночью не пишем | окно тишины считается в **часовом поясе зрителя**; ночное письмо возвращается в очередь и ждёт утра |
| Отписался — не пишем | подписки проверяются при планировании; ссылка отписки **своя у каждого получателя** (идентификатор и подпись) и работает без входа в аккаунт. Отказ от всего хранится отдельным признаком зрителя: у того, кто ничего не настраивал, выключать было бы нечего |
| Простой генератора не превращается в лавину | у запуска рассылки есть ключ периода с уникальным индексом |

### Что защищает систему от отказов

Сообщение не теряется ни на одном шаге. **API и генератор рассылок в брокер
не пишут**: событие (или запуск рассылки) и задание на публикацию ложатся в
базу одной транзакцией — это outbox, — а в RabbitMQ задания переносит
отдельный процесс `notify-relay`. Брокер лежит — задания ждут в базе и уходят,
когда он поднимется; вызывающий получает `accepted: true` и ничего не теряет.
Дальше — публикация с подтверждением, очереди `durable`, сообщения
`delivery_mode=2`, подтверждение только после успешной обработки. Гарантия — **at least once**, а от дублей защищает ключ
идемпотентности: `exactly once` через SMTP недостижим в принципе — сервер
может принять письмо и не успеть ответить.

Временная ошибка не останавливает очередь: сообщение уходит в **Dead Letter
Exchange** и возвращается через `notify.<этап>.retry` спустя
`NOTIFY_RETRY_DELAY`. После `NOTIFY_MAX_ATTEMPTS` попыток оно садится в
`notify.dead` и ждёт человека. Без этого один негодный адресат крутился бы в
цикле и держал бы всю рассылку — ровно то, чем пугает задача урока про
RabbitMQ.

## Запуск

Сервис поднимается вместе со всем кинотеатром:

```sh
cp .env.example .env     # задайте AUTH_SERVICE_TOKEN, NOTIFY_POSTGRES_PASSWORD, RABBIT_PASSWORD
docker compose up -d --build
```

Появится семь контейнеров сервиса (`notify-api`, три воркера,
`notify-relay`, `notify-scheduler`, `notify-ws`), брокер `rabbitmq` и приёмник почты `mailpit`.

| Что | Где |
|---|---|
| Документация API | http://localhost/notify/api/openapi |
| Письма стенда | http://localhost:8025 (Mailpit) |
| Очереди брокера | http://localhost:15672 (логин и пароль — `RABBIT_USER` / `RABBIT_PASSWORD`) |
| Рассылки менеджера | http://localhost/admin/mailings/ |

Письма на стенде **никуда не уходят**: их принимает Mailpit, и там видно
письмо целиком — тему, тело, адрес. Для настоящего почтового сервера
достаточно сменить `NOTIFY_SMTP_*`; код при этом не меняется.

## Что умеет API

| Метод | Адрес | Кто ходит |
|---|---|---|
| `POST` | `/notify/api/v1/events` | сервисы кинотеатра: событие → очередь |
| `GET/POST/PUT/DELETE` | `/notify/api/v1/templates…` | админ-панель: шаблоны писем |
| `POST` | `/notify/api/v1/templates/preview` | админ-панель: посмотреть письмо, не сохраняя |
| `GET/POST` | `/notify/api/v1/campaigns…` | админ-панель: рассылки, запуск и отмена |
| `GET` | `/notify/api/v1/me/notifications` | зритель: свои уведомления |
| `GET/PUT/DELETE` | `/notify/api/v1/me/subscriptions` | зритель: настройки уведомлений |
| `GET` | `/notify/api/v1/unsubscribe` | зритель из письма, **без входа** |
| `GET` | `/notify/api/v1/me/email-confirmation` | зритель: подтверждён ли адрес почты |
| `GET` | `/notify/api/v1/confirm-email?token=…` | зритель из приветственного письма: одноразовый токен, привязанный к адресу |
| `POST` | `/notify/api/v1/links` | сокращение ссылки |
| `GET` | `/s/{key}` | переход по короткой ссылке: 302 или 404, если срок вышел |
| `WS` | `/ws/notifications?token=…` | зритель: мгновенные уведомления в открытую вкладку |

Служебные эндпоинты опознают вызывающего по заголовку `X-Service-Token`, а
личный кабинет — по access-токену сервиса авторизации. **Websocket тоже
требует токен**: без него к чужому потоку уведомлений подключился бы кто угодно.

### Пример: отправить событие

```sh
curl -X POST http://localhost/notify/api/v1/events \
  -H "X-Service-Token: $AUTH_SERVICE_TOKEN" -H 'Content-Type: application/json' \
  -d '{
        "event_id": "0f0e7c9c-6b28-4f0e-9f6a-6a1a4b1f2b3c",
        "routing_key": "film-reporting.v1.episode-added",
        "template_code": "new_episode",
        "audience": {"kind": "users", "user_ids": ["<uuid зрителя>"]},
        "content_id": "series-42", "content_version": 8,
        "context": {"film_title": "Матрица", "episode": 8}
      }'
```

Повтор того же запроса вернёт `"accepted": false` и второго письма не создаст.

## Шаблоны писем

Шаблонизатор — **Jinja2** в песочнице, с автоэкранированием. Менеджеру
доступен ограниченный набор переменных (`first_name`, `full_name`,
`film_title`, `unsubscribe_url` и ещё несколько — полный список в описании
эндпоинта), и шаблон **проверяется при сохранении**: разбирается синтаксис,
сверяются переменные и письмо действительно рендерится на тестовых данных.
Без этой проверки шаблон с опечаткой или бесконечным циклом обнаружился бы во
время рассылки, когда половина писем уже ушла.

Каждая правка повышает версию шаблона, и в сообщение очереди едет пара
«код, версия»: рассылка, начатая со старым текстом, старым текстом и
досылается.

Четыре стартовых шаблона заводит миграция: `welcome`, `weekly_digest`,
`monthly_summary`, `new_episode`.

## Рассылки менеджера

Страницы менеджера живут в общей админке: http://localhost/admin/mailings/.
Они ничего не хранят у себя — шаблоны и рассылки лежат в этом сервисе, а
админка ходит к нему по HTTP. Три способа запуска:

* **сразу** — ни времени, ни расписания;
* **отложенно** — `scheduled_at`, запуск подхватит генератор;
* **повторяемо** — `cron` из пяти полей: `0 18 * * 5` — каждую пятницу в 18:00.

## Настройки

Все переменные с префиксом `NOTIFY_` (`.env` общий для всех сервисов
кинотеатра). Исключения — два общих секрета сервиса авторизации:
`AUTH_JWT_SECRET_KEY` (подпись токенов) и `AUTH_SERVICE_TOKEN` (служебный
доступ). Полный список с пояснениями — в [src/core/config.py](src/core/config.py)
и [.env.example](../.env.example).

Роль воркера задаётся переменной `NOTIFY_WORKER_ROLE` = `plan` | `render` |
`send`: образ один, процессов четыре.

## Тесты

```sh
# Unit: бизнес-логика на хранилищах в памяти, без Docker
cd notifications/tests/unit && pytest

# Функциональные: сервис, брокер, почта и настоящий сервис авторизации в изолированном compose
docker compose -f notifications/tests/functional/docker-compose.yml up --build \
    --abort-on-container-exit --exit-code-from tests
```

Функциональные тесты поднимают **настоящий** сервис авторизации, а не
заглушку: воркер ходит в его справочник контактов, и именно этот стык чаще
всего и ломается. Письмо проверяется в почтовом ящике Mailpit через его
HTTP-API — тема, тело, адрес, — а не по журналу отправителя: иначе
проверялось бы намерение сервиса, а не результат.

Линтеры:

```sh
cd notifications && ruff check . && flake8 . && mypy src
```

## Чего здесь нет

* **SMS и push.** Канал — это реализация интерфейса `channels/base.py`;
  добавление нового не трогает ни API, ни планировщик, ни админ-панель. Но
  реализован только email (и websocket для мгновенных сообщений).
* **Маркетинговая сегментация.** Сегмент приходит в рассылку готовым списком
  или правилом; строить его — работа аналитики, и урок «Единая политика
  контактов» выводит её за рамки задачи.
* **Отслеживание прочтения** (пиксель, MDN). В истории отправок есть поле
  результата, но факты открытия писем не собираются.
