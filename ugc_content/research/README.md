# Исследование хранилищ: MongoDB и PostgreSQL

Задание 2 девятого спринта: выбрать хранилище для лайков, рецензий и закладок —
наполнить базы 10+ млн записей, прогнать нагрузочные тесты и подтвердить выбор
числами.

> **Статус: каркас.** Здесь описаны методика и окружение; генератор, скрипты
> замеров и результаты появятся по ходу эпика E2
> ([docs/planning-sprint9.md](../../docs/planning-sprint9.md)).

Задание спринта называет MongoDB как хранилище будущего API, но выбор всё равно
нужно проверить: требование «чтение не дольше 200 мс» жёстче всего, что было в
проекте раньше, и если MongoDB его не держит на нужных сценариях, менять
придётся и хранилище, и модели сервиса. Сравнение идёт с PostgreSQL — он уже
есть в проекте (каталог фильмов, сервис авторизации), и выбирать новое
хранилище имеет смысл, только если оно лучше знакомого.

## Что меряем

| Замер | Почему он |
|---|---|
| Чтение на загруженных данных | Сценарии из урока: количество лайков и дизлайков фильма, средняя оценка, список понравившихся фильмов, список закладок. Именно они выполняются при каждом открытии карточки и обязаны уложиться в 200 мс |
| Чтение свежих данных | Поставили лайк — через какое время он виден в этих сценариях. Для пользователя «лайк не появился» и «сервис сломался» — одно и то же |
| Вставка, записей/с | Второстепенный критерий: подсказка урока прямо говорит, что скорость записи здесь не так важна, как скорость чтения |
| Место на диске | Во что превращаются 10 млн записей — от этого зависит стоимость хранения |

Условия одинаковы для обоих хранилищ: одна машина, один и тот же набор данных
(один генератор с фиксированным зерном), одни и те же сценарии, одинаковые
ограничения по процессорам и памяти в compose.

Замеры даются перцентилями (p50, p95, p99), а не средним: среднее время ответа
прячет как раз те запросы, из-за которых карточка фильма грузится долго.

## Данные

Объём считается по формуле урока:

```
S(<DataType>) = S(Viewing History) × AverageDataUnitSize,   S(Viewing History) = UsersCount × MoviesCount
```

Правдоподобное распределение важнее объёма: фильмы — по Парето (несколько хитов
и длинный хвост), активность зрителей тоже неравномерна. На равномерном шуме
любое хранилище выглядит одинаково хорошо, а разница видна как раз на горячих
фильмах, у которых сотни тысяч оценок.

## Окружение

[`docker-compose.yml`](docker-compose.yml) поднимает оба хранилища:

* **MongoDB** — шардированный кластер, как в уроке: два шарда по три узла
  реплик, три сервера конфигурации и два маршрутизатора mongos. Клиент ходит
  только через mongos.
* **PostgreSQL** — один узел: сравнивать кластер с одиночным сервером нечестно,
  но у PostgreSQL в этом проекте и нет кластера, а вопрос исследования —
  «что выбрать для сервиса», а не «что быстрее при равном железе».

```sh
docker compose -f ugc_content/research/docker-compose.yml up -d
# после старта кластер нужно собрать: инициализировать наборы реплик,
# представить шарды маршрутизаторам, включить шардирование коллекций
./ugc_content/research/init_cluster.sh     # появится вместе с исследованием
```
