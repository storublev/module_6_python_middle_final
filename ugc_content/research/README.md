# Исследование хранилищ: MongoDB и PostgreSQL

Задание 2 девятого спринта: выбрать хранилище для лайков, рецензий и закладок —
наполнить базы 10+ млн записей, прогнать нагрузочные тесты и подтвердить выбор
числами.

Задание спринта называет MongoDB как хранилище будущего API, но выбор всё равно
нужно проверить: требование «чтение не дольше 200 мс» жёстче всего, что было в
проекте раньше. Сравнение идёт с PostgreSQL — он уже есть в проекте (каталог
фильмов, сервис авторизации), и брать новое хранилище имеет смысл, только если
оно лучше знакомого.

## Главный результат

**Дело оказалось не в выборе хранилища, а в способе считать агрегат.** Ни
MongoDB, ни PostgreSQL не укладываются в 200 мс, если «сколько лайков у фильма»
считать на лету: у популярного фильма сотни тысяч оценок, и подсчёт идёт
**секундами**. Оба укладываются с огромным запасом, если агрегат хранится
готовым и двигается при каждой оценке.

| Сценарий (10 млн оценок) | MongoDB p95 | PostgreSQL p95 | Бюджет |
|---|---|---|---|
| Агрегат по горячему фильму **на лету** | 3 327 мс | 9 124 мс | ❌ 200 мс |
| Агрегат по горячему фильму **из счётчика** | **0,66 мс** | **0,20 мс** | ✅ |
| Агрегат по случайному фильму на лету | 18,8 мс | 12,6 мс | ✅ (но у хвоста мало оценок) |
| Агрегат по случайному фильму из счётчика | 0,81 мс | 0,39 мс | ✅ |

Отсюда решение сервиса: коллекция `film_ratings` обновляется вместе с оценкой
(`$inc` на разницу), а карточка фильма читает одну запись по ключу. Подробности
— в [ugc_content/README.md](../README.md), раздел «Почему агрегат хранится
готовым».

## Что меряли

| Замер | Почему он |
|---|---|
| Чтение на загруженных данных | Сценарии из урока: количество лайков и дизлайков фильма, средняя оценка, список понравившихся фильмов, список закладок, рецензии с сортировками |
| Отдельно — горячие фильмы | У хита сотни тысяч оценок, у фильма из хвоста десяток. Если мерить вперемешку, редкие тяжёлые запросы утонут в массе лёгких |
| Свежесть | Через сколько поставленная оценка видна в агрегате (НФТ-6) |
| Чтение под нагрузкой | То же самое, пока два процесса непрерывно пишут |
| Вставка и место на диске | Второстепенное: подсказка урока прямо говорит, что скорость записи здесь не так важна, как скорость чтения |

Время даётся **перцентилями** (p50/p95/p99), а не средним: среднее прячет как
раз те запросы, из-за которых карточка грузится долго.

## Условия

Одинаковые для обоих: одна машина, контейнеры с равными пределами (2 CPU, 4 ГБ
памяти), 1 ГБ под кеш (`wiredTigerCacheSizeGB=1` и `shared_buffers=1GB`), один
и тот же набор данных от одного генератора с фиксированным зерном, одни и те же
сценарии, одинаковый размер пачки при вставке.

Схемы не одинаковые, а **равноценные**: каждому хранилищу даны индексы, которые
оно само считает правильными для этих запросов (см. `storages.py`). Мерить
MongoDB без индексов против PostgreSQL с индексами — значит мерить не
хранилища. PostgreSQL после загрузки выполняет `ANALYZE`: без статистики его
планировщик считает таблицы пустыми. Это не фора, а выравнивание — в бою
статистику собирает autovacuum.

## Данные

10 000 000 оценок, 2 000 000 закладок, 20 000 рецензий — доли те же, что в
[метриках нагрузки](../../docs/requirements-sprint9.md): на 500 000 оценок в
сутки приходится 100 000 закладок и 1 000 рецензий. По объёму это примерно три
недели работы кинотеатра.

Фильмы распределены **логарифмически равномерно** (плотность ~1/x): на самый
популярный фильм приходится около 6% оценок, на первую двадцатку — 28%, хвост
из десятков тысяч фильмов получает единицы. Сначала пробовали Парето с длинным
хвостом, но на таком каталоге оно вырождается: один фильм забирает больше трети
всех оценок, чего в жизни не бывает.

Пары «зритель — фильм» уникальны **по построению**, а не по удаче: фильм
выводится из номера зрителя детерминированным хешем, повторные записи того же
зрителя сдвигаются на единицу. Случайный выбор на десяти миллионах записей даёт
совпадения сотнями, и загрузка падает на уникальном индексе в середине.

## ADR-6. Хранилище пользовательского контента — MongoDB

**Контекст.** Нужно хранить лайки, рецензии и закладки: 550 млн оценок за три
года, чтение за 200 мс, структура данных простая и своя у каждой сущности.
Кандидаты — MongoDB (её предлагает задание спринта) и PostgreSQL (уже есть в
проекте).

**Решение.** MongoDB.

**Почему не PostgreSQL, хотя по замерам он быстрее.** В цифрах PostgreSQL
выигрывает на всех сценариях — в два-пять раз. Но обе базы укладываются в
бюджет с запасом в двести раз (0,2–0,8 мс против 200 мс), поэтому разница в
полмиллисекунды не аргумент. Аргументы, которые остаются:

* **Горизонтальное масштабирование из коробки.** 550 млн оценок и рост от числа
  зрителей — это тот случай, ради которого в MongoDB встроено шардирование:
  добавить шард можно, не меняя код (НФТ-9). В PostgreSQL шардирование — это
  внешние решения и ручная работа.
* **Данные сами по себе документные.** Рецензия с голосами и счётчиками — один
  документ; соединять нечего, ссылочная целостность не нужна, а связей между
  сущностями почти нет.
* **Разные сервисы — разные хранилища.** Каталог фильмов и учётные записи
  лежат в PostgreSQL, и наливать в тот же кластер поток пользовательского
  контента — значит связать их общей судьбой: всплеск лайков ударит по входу в
  кинотеатр.
* **Учебная цель модуля.** Спринт про то, как выбирают и осваивают новое
  хранилище; взять привычный PostgreSQL значило бы не сделать задание.

**Чем платим.** Нет транзакций на одиночном mongod (счётчик и оценка пишутся
двумя операциями — см. ниже), слабее инструменты отчётности, а операции нужно
уметь сопровождать: кластер из 11 контейнеров сложнее одного сервера.

## ADR-7. Агрегат по фильму хранится готовым

**Контекст.** Карточка фильма показывает лайки, дизлайки и среднюю оценку при
каждом открытии — 420 запросов в секунду в пике. Подсчёт на лету занимает у
популярного фильма 1–9 секунд (замеры выше).

**Решение.** Держать готовый агрегат отдельной записью (`film_ratings`) и
двигать его на каждую оценку операцией `$inc`; среднее хранить как сумму и
количество, а не как число.

**Последствия.** Чтение карточки — 0,5 мс вместо секунд, и время не зависит от
популярности фильма. Взамен: оценка и счётчик пишутся двумя операциями, и на
одиночном mongod между ними нет транзакции — при падении ровно между записями
счётчик разойдётся на единицу. Лечится полным пересчётом
(`bench.py counters` делает его за 9 секунд на 10 млн записей) и полностью
уходит на наборе реплик, где обе записи заворачиваются в транзакцию.

## ADR-8. Пользовательский контент — отдельный сервис

**Контекст.** Урок предлагает развилку: добавить функциональность в
существующий сервис сбора событий или сделать новый.

**Решение.** Отдельный сервис `ugc_content`.

**Почему.** У сервиса сбора событий противоположный профиль: «принять и
забыть», запись в Kafka, ноль чтений, требование — не потерять поток в 4 200
событий в секунду. Здесь — чтение за 200 мс, CRUD, своё хранилище. Слив их в
один сервис, мы получили бы общий пул воркеров, где тяжёлое чтение карточек
конкурирует с приёмом событий, и общий релизный цикл для двух разных задач.
Плюс у них разные хранилища, а «зоопарк в одном сервисе» — ровно то, чего
советует избегать урок.

**Чем платим.** Ещё один сервис в сопровождении, ещё один образ, ещё один
маршрут в nginx и общая с остальными настройка секрета токенов.

## Как воспроизвести

```sh
# поднять хранилища (2 CPU и 4 ГБ на каждое)
docker compose -f ugc_content/research/docker-compose.yml up -d

# прогнать замер целиком: загрузка → счётчики → чтение → свежесть → под нагрузкой
.venv/bin/python ugc_content/research/bench.py all --storage mongodb \
    --rows 10000000 --repeat 200 --report results-mongodb.json
.venv/bin/python ugc_content/research/bench.py all --storage postgresql \
    --rows 10000000 --repeat 200 --report results-postgresql.json

# или одной командой
make -C ugc_content/research all

# убрать данные: они занимают несколько гигабайт
make -C ugc_content/research clean
```

Отдельные шаги: `load`, `counters`, `read`, `freshness`, `read-under-load`.

**Осторожно с местом на диске.** Десять миллионов записей — это около 2 ГБ
данных в каждом хранилище плюс до 4 ГБ журнала предзаписи у PostgreSQL
(`max_wal_size=4GB`). Прогон обоих хранилищ подряд требует порядка 10 ГБ
свободного места, и на macOS образ диска Docker после удаления томов сам не
сжимается — место возвращает `docker/desktop-reclaim-space`.

## Шардированный кластер

Скорость меряли на одиночных узлах — иначе сравнивались бы не хранилища, а
железо. Отдельно собран кластер из урока: два шарда по три узла реплик, три
сервера конфигурации и два маршрутизатора mongos.

```sh
docker compose -f ugc_content/research/docker-compose.cluster.yml up -d
./ugc_content/research/init_cluster.sh
```

Ключи шардирования выбраны по запросам, а не по «равномерности»: оценки и
рецензии шардируются по `film_id` (карточку фильма спрашивают по фильму),
закладки — по `user_id` (список закладок спрашивают по зрителю). Хешированный
ключ, а не диапазонный: идентификаторы — UUID, и диапазон по ним превратился
бы в один горячий чанк.
