# Сервис пользовательского контента

Лайки, рецензии и закладки онлайн-кинотеатра. Отдельный сервис, а не часть
[сервиса сбора событий](../ugc/README.md): у того требование «принять и забыть»
и запись в брокер, а здесь — чтение за **200 мс** на каждый показ карточки
фильма и полноценный CRUD.

Требования, из которых сервис вырос, — [docs/requirements-sprint9.md](../docs/requirements-sprint9.md);
выбор хранилища и замеры — [research/](research/README.md).

## Как он устроен

```
клиент ──(Bearer access-токен)──► nginx /content/ ──► ugc-content ──► MongoDB
```

* **FastAPI + Beanie** поверх асинхронного клиента pymongo. Так же устроены
  Async API и сервис авторизации, а Beanie — ODM из урока: модели наследуются
  от `beanie.Document`, то есть от `pydantic.BaseModel`.
* **Токен проверяется на месте**, без обращения к сервису авторизации: подпись
  HS256 тем же секретом, которым токен выпущен, плюс срок действия и тип. На
  каждое открытие карточки ходить в Auth значило бы сделать его узким местом.
* **Чтение агрегата — это чтение одной записи.** Лайки, дизлайки и сумма
  оценок лежат готовыми в коллекции `film_ratings` и двигаются на каждую
  оценку. Почему не считать на лету — ниже.
* **Публичное и личное разделено:** агрегаты и списки рецензий видит любой
  посетитель, всё, что привязано к зрителю, требует токена.

Слои те же, что у остальных сервисов проекта:

| Каталог | Что внутри |
|---|---|
| `src/api` | HTTP: маршруты, формат ошибок, проверка токена, идентификатор запроса |
| `src/core` | Настройки, журнал в JSON, трассировка, Sentry |
| `src/models` | Контракт лайков, рецензий и закладок на pydantic |
| `src/services` | Бизнес-логика: оценки, рецензии, закладки |
| `src/storage` | Интерфейсы хранилища, документы MongoDB и реализация |

Бизнес-логика зависит от интерфейсов из `storage/base.py` и не импортирует ни
FastAPI, ни pymongo: в unit-тестах на место хранилища встаёт реализация в
памяти, а конкретные классы выбираются в одном месте — `api/dependencies.py`.

## Почему агрегат хранится готовым

Это главное решение сервиса, и оно взято не из головы, а из
[замеров](research/README.md). На десяти миллионах оценок подсчёт «сколько
лайков у фильма» конвейером агрегации занимает:

| Фильм | Подсчёт на лету | Чтение готового счётчика |
|---|---|---|
| Из хвоста каталога (десяток оценок) | единицы миллисекунд | доли миллисекунды |
| Из первой двадцатки (сотни тысяч оценок) | **секунды** | доли миллисекунды |

Бюджет ответа — 200 мс, и карточка популярного фильма в него не укладывается
никак. Поэтому `film_ratings` обновляется вместе с оценкой (`$inc` на разницу
между старой и новой), а чтение карточки — это `find_one` по ключу.

Чем платим: счётчик и сама оценка пишутся двумя операциями, и на одиночном
mongod между ними нет транзакции. Если процесс умрёт ровно между ними, счётчик
разойдётся с оценками на единицу. Лечится это полным пересчётом (тем же, что
делает `research/bench.py counters`), а на наборе реплик обе записи
заворачиваются в одну транзакцию.

## Индексы: порядок полей решает

Список понравившихся фильмов фильтрует оценки `>= 6` и сортирует по дате. Если
в индексе поставить `rating` перед `created_at`, он **перестаёт давать порядок
по дате**: условие на диапазон разбрасывает подходящие записи по разным
значениям оценки, и MongoDB добавляет в план отдельный этап `SORT` — то есть
сортирует выборку в памяти.

Поэтому индекс частичный: `(user_id, created_at)` с условием `rating >= 6`.
Условие переехало из запроса в сам индекс, и дизлайки в нём не хранятся вовсе.
Разница на 200 оценках зрителя:

| | План | Прочитано ключей на страницу в 20 записей |
|---|---|---|
| `(user_id, rating, created_at)` | `FETCH ← SORT ← IXSCAN` | все подходящие (135) |
| `(user_id, created_at)` при `rating >= 6` | `LIMIT ← FETCH ← IXSCAN` | ровно 20 |

Планы проверяются тестами (`tests/functional/src/test_indexes.py`), а не
глазами: индекс, который есть, но не используется, хуже отсутствующего — он
берёт плату с каждой записи и ничего не ускоряет.

Лишние индексы удаляются при старте (`allow_index_dropping=True` в
`init_beanie`): единственный источник правды — `storage/documents.py`.

## API

Все адреса — с префиксом `/content/api/v1`, документация — `/content/api/openapi`.

| Метод и адрес | Что делает | Токен |
|---|---|---|
| `PUT /films/{film_id}/rating` | поставить или изменить оценку 0–10 | нужен |
| `DELETE /films/{film_id}/rating` | снять свою оценку | нужен |
| `GET /films/{film_id}/rating/me` | своя оценка фильма | нужен |
| `GET /films/{film_id}/rating` | лайки, дизлайки, средняя оценка | не нужен |
| `GET /users/me/likes` | понравившиеся фильмы (оценка ≥ 6) | нужен |
| `PUT /films/{film_id}/bookmark` | отложить фильм (идемпотентно) | нужен |
| `DELETE /films/{film_id}/bookmark` | убрать из закладок | нужен |
| `GET /users/me/bookmarks` | свои закладки | нужен |
| `POST /films/{film_id}/reviews` | написать рецензию | нужен |
| `GET /films/{film_id}/reviews` | рецензии фильма с сортировкой | не нужен |
| `DELETE /reviews/{review_id}` | удалить свою рецензию | нужен |
| `PUT /reviews/{review_id}/vote` | оценить полезность **чужой** рецензии | нужен |
| `GET /health`, `GET /ready` | живость и готовность | не нужен |

Ошибки — в том же формате, что у сервиса авторизации:
`{"code": "review_not_found", "detail": "Review not found"}`. Коды и статусы
описаны в OpenAPI у каждого эндпоинта.

Решения, которые видно по методам:

* **`PUT`, а не `POST`** у оценки и закладки: обе операции идемпотентны, и
  повторный запрос (клиент не дождался ответа и повторил) не должен создавать
  вторую запись.
* **Чужая рецензия — 403, а не 404**: она существует, её просто нельзя
  удалить. Прятать факт существования публичной рецензии незачем.
* **За свою рецензию голосовать нельзя** — 403 `own_review_vote`: иначе автор
  накрутил бы себе полезность и поднял свой текст в сортировке «самые
  полезные».
* **Сортировок рецензий несколько** (`newest`, `oldest`, `most_useful`,
  `highest_rating`): показывать только самые залайканные — ловушка, новая
  рецензия никогда не наберёт голосов и не поднимется наверх.

## Запуск

В общем стеке кинотеатра он поднимается сам:

```sh
docker compose up -d ugc-content
curl http://localhost/content/api/v1/films/<film_id>/rating
```

Отдельно, без остального стека:

```sh
docker compose -f ugc_content/tests/functional/docker-compose.yml up -d mongo content
```

Настройки — переменные с префиксом `CONTENT_` (см. `.env.example`), ключ
подписи токенов — общий `AUTH_JWT_SECRET_KEY`.

## Проверка живого стенда

Сквозной сценарий по поднятому стеку — одной командой из корня репозитория:

```sh
docker compose up -d
./scripts/check_stack.sh
```

Скрипт заводит своего зрителя и свой фильм, поэтому его можно запускать на
работающем стенде: чужие данные он не трогает.

## Тесты

```sh
# unit: бизнес-логика на хранилищах в памяти, без Docker
cd ugc_content/tests/unit && python -m pytest

# функциональные: сервис и MongoDB в изолированном compose
docker compose -f ugc_content/tests/functional/docker-compose.yml up --build \
    --abort-on-container-exit --exit-code-from tests
```

Функциональные тесты ходят к сервису по HTTP и проверяют записанное прямо в
MongoDB; код сервиса они не импортируют. Данные каждый тест готовит и чистит
сам — по своим идентификаторам фильма и зрителя.

## Наблюдаемость

* Журнал — **JSON в stdout**, по записи на строку, с `request_id`,
  уровнем и именем сервиса. Доставкой в ELK занимается сборщик рядом
  ([deploy/observability/](../deploy/observability/README.md)), а не само
  приложение: иначе смена системы логирования означала бы правку кода.
* Неотловленные исключения уходят в **Sentry**, если задан `CONTENT_SENTRY_DSN`.
  Тела запросов не отправляются: в них тексты рецензий.
* Спаны — в **Jaeger** по OTLP, если задан `CONTENT_OTLP_ENDPOINT`.
